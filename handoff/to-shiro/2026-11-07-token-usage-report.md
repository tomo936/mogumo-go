## 3. 何に多く使ったか
1. **Blender で模型を作る作業**（LOD 実装の 21.7万の大半）。800 三角形まで減らす → 穴があく → 作り方を変えて作り直す、の試行錯誤。
2. **画面を撮って原因を確かめる調査**（経堂駅・雲の中のお店）。確認用ページの起動・撮影・比較画像の作成でツール回数が増える。ただし推測で直して外すより結果的に安い。
3. **設計メモ**（1本 8〜15万）。仕様・基本設計・DB 設計・今のコードを読み直すため。

## 4. うまくいったこと
- サブに「自分で完結する指示」（読む場所・決定済みのこと・終わりの条件・報告の形）を渡すと、リーダーの文脈がほとんど増えない。
- 小さい修正（数行・1ファイル）はリーダーが直接やり、サブを起こさない（起こすたびに読み直しの費用がかかる）。
- オーナーへの確認は画像1枚（PNG）にまとめると、言葉の往復が減る（ピンの説明の図など）。

## 5. 失敗・ムダだったこと
- `git push` を `git -C …` や `&&` つなぎで実行して許可が通らず、オーナーの手をわずらわせた（単独のコマンドなら通る）。
- 設計役の見積もりの前提（模型 約9,000 三角形）が実物（約7,000）と違った。最初に測ってから見積もるべきだった。
- 利用上限に当たり、作業が一時止まった。重いサブ（Blender・画面撮影）を続けて走らせると上限に近づきやすい。

## 6. これからの工夫（案）
- 重いサブ（Blender・画面撮影）は1つずつ。並べて走らせるのは文書だけの作業（設計メモなど）に限る。
- 設計の前に「測る」小さい段を置く（数字の前提を実物で確かめてから見積もる）。
- 画像の確認は、比較を1枚にまとめた PNG で（枚数を減らす）。
- シロ側も、素材の依頼ファイルに「用途・大きさ・画風・置き場所」がそろっていれば、こちらの読み直しが減ります。
