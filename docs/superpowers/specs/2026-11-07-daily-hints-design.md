# 設計: 気配・デイリー（今日の気配3件）

日付: 2026-11-07。設計役が作成。前の段は `2026-11-06-hotpepper-checkin-design.md`（チェックイン）と `2026-11-07-shop-lod-design.md`（お店を全部出す）。
この段はコードを書く前の設計メモ。実装は実装役が行う。

用語の言いかえ（このメモで使うもの）
- **Edge Function**: Supabase の上で動く、サーバー側の小さなプログラム。秘密の鍵はここでだけ使える。
- **RLS**: DB の「行ごとの読み書きの許可」。本人の行しか読めない、などを DB 自身が守る。
- **migration（マイグレーション）**: DB の形を変える手順書（SQL のファイル）。番号順に流す。
- **トランザクション**: 「全部成功するか、全部取り消すか」のひとまとまりの書き込み。
- **RPC / SQL 関数**: DB の中に置いた手続き。Edge Function から1回呼ぶと、中身が1つのトランザクションで動く。
- **一意制約**: 「同じ組み合わせの行を2つ作れない」という DB の決まり。二重登録を DB が止める。
- **HTML マーカー**: 地図の上に重ねて置く、ふつうの画面部品（ボタンなど）。地図の絵の中ではなく、その手前に出る。
- **domain / infra / ui**: CLAUDE.md の3つの置き場所（決まりと計算／外とのつなぎ／画面）。

## 1. 意図と理由

- SPEC S4 で、デイリークエストは「**毎日3件、すべて『気配』型**。行き先は霧の中の未訪問店で、店名は伏せ、気配（ヒント）だけを出す。利用者は3件から選んで行く」と決まっている。案B（霧の向こうのお題）の芯で、「まだ行ったことのない店へ行く理由」を毎日つくるのがねらい。
- ここまでで、地図・霧・お店・チェックインがそろった。気配はこれらを組み合わせるだけで作れる段階にある。次の図鑑（未訪問カードは「気配と同じ出し方」S11）にも、ここで作るヒントの出し方がそのまま使える。
- 決め方の根拠（正本の引用）
  - S5: 「気配は **霧（モヤ）の中にピンが刺さった形** で地図に出す。ピンには店名を出さず、**曖昧な特徴を少しだけ**出す（例: ジャンルを『中華？』と曖昧に、その店の個性を少し）。**気配をタップするとカメラがその場所へ移動する**。店名が明かされるのは **店から 30m 以内**」。「ジャンルが分からない店は **たまに出る『謎の気配』枠**」。「個性ヒントの材料は **お店のキャッチコピーの断片＋予算帯の両方**」。
  - S10: 「デイリーの気配は、**自宅の範囲の外にいる時は今いる場所の周りからも出す**」。
  - S15: 「選ばなかった気配は翌朝リセット。気配の店が無い日は『今日は気配なし』表示＋近くの未訪問店を通常ピンで案内」。
  - S16: 「気配ピン（霧の中）は…アイコンに『？』を重ねてぼかした表示にする」。
  - S17: 「下部中央に大きな丸ボタン『探索』を置き、タップで探索シートが開く。探索シートの中身は、今日の気配3件／週ミッションの進捗／図鑑・記録・マイページへの入口」。
  - §9（2026-11-05）: 「**気配は『端末が候補、サーバーが抽選』**: 端末が自宅1kmの霧の中の未訪問店（圏外では現在地周りも）の候補を送り、サーバーがランダムに3件選ぶ。生成はその日に初めてアプリを開いたときの1回。気配の店名は端末の画面で伏せるだけ（D-17、U-10、N-04）」。
  - §8・§9: コインは「チェックイン30／気配の店はボーナス+10で40」。「同じ店のコインは1日1回まで（D-15）」。さらに 2026-11-07 本人決定で「**同じ店のチェックインは1日1回まで**…日の区切りは JST 0時」。
  - DB 設計 3.10・D-17・D-19、基本設計 6.2・U-10・N-04。
- 2026-11-07 のオーナー決定（今回の会話の正本）
  - 気配の対象は、基本は**ホットペッパーの情報（キャッチ・予算・ジャンル）がある店**（`hp:` を持つ店）。地図データだけの店（`osm:` だけ）は「謎の気配」として**たまに**混ぜる。
  - リーダーの判断: 「たまに」は **4日に1回くらい、その日の3件のうち1件を謎の気配にする**（確率は調整値）。
  - 気配のピンは **HTML マーカー**（ビルのピンと同じ方式。雲の上に見える）。

## 2. 目標・しないこと・失敗とみなすこと

### 目標（今回やること）
1. 地図の下の真ん中に大きな丸い「探索」ボタン。押すと探索シートが開く。シートの中身は **今日の気配3件だけ**。
2. 今日の気配の生成: その日（日本時間）に初めて地図を開いたとき、端末が候補を集めて送り、サーバーが3件を抽選して保存する。2回目以降は保存したものを読むだけ。
3. 気配のピン: 霧の中の店の位置に、仮の丸＋「？」の HTML マーカー。シロのアイコン13種が届いたら差し替える。
4. ピン（または探索シートの気配）を押すと、カメラがその場所へ移動し、ヒントのシートが開く（店名は伏せる）。
5. 店から 30m 以内に入ったら店名を明かす。まずは簡単な演出（ピンがぽんと弾む＋帯で店名）。
6. 気配の店にチェックインしたら +10（合計40）。`checkins.was_hint = true`、`daily_hints.completed_checkin_id` に記録。
7. 翌朝（日本時間0時）リセット: 日付が変わったら昨日の気配は消え、新しい気配を作る。
8. 気配なしの日の表示: 「今日は気配なし」＋近くの未訪問店の案内。

### しないこと（次の段以降）
- 週ミッション（探索シートの「週ミッションの進捗」欄も今回は出さない）
- 探索シートの図鑑・記録・マイページへの入口（画面がまだ無い）
- 気配までの距離・方角の表示（SPEC §2.4 の例「北東 400m」はあるが決定ではない → §15 で確認）
- シロのアイコン13種への差し替え（届いてから）
- 気配の選び直し・追加・通知
- 気配の店の詳しい画面（N-04 の決定どおり、伏せた状態のヒントのシートだけ）

### 失敗とみなすこと
- 店名が、30m に入る前（またはチェックインする前）に画面のどこかに出る（探索シート・ヒントのシート・お店のシート・ビルの一覧・ピン）。
- 自宅の座標や現在地がサーバーに送られる、または Edge Function のログに出る。
- 同じ日に気配が2組できる。アプリを開き直すと気配が変わる。
- 気配の店にチェックインして +10 が付かない、2回付く、気配でない店に付く、昨日の気配の店で付く。
- 日本時間0時を過ぎても昨日の気配が出たまま。
- 気配の取得を待って地図の表示が遅れる（D-17「地図表示は待たせず裏で取得」）。
- iPhone で目に見えて重くなる。

## 3. 制約（非機能要件）

### 3.1 秘密情報（どこで持ち、どこへ出さないか）
| 秘密 | 持つ場所 | 出してはいけない場所 |
|---|---|---|
| `HOTPEPPER_API_KEY` | Supabase の Secrets。読むのは `shops-hotpepper` だけ | ブラウザのコード、`.env` の `VITE_` で始まる値、ログ、`daily-hints`（今回の関数はホットペッパーに問い合わせないので、鍵は**不要**） |
| `SUPABASE_SERVICE_ROLE_KEY`（何でも書ける強い鍵） | Edge Function の環境変数（`daily-hints`・`checkin`・`shops-hotpepper`） | ブラウザのコード・ログ・返す値 |
| 利用者のトークン（JWT） | ブラウザ（Supabase のログイン状態）→ 要求のヘッダー | ログ |
| **自宅の座標** | 端末の localStorage `mogumo.home.<userId>` だけ | サーバーへの要求・DB・ログ・URL。**自宅からの距離・方角も送らない** |
| 現在地 | 端末だけ | `daily-hints` には送らない（`checkin` は 50m 判定のため従来どおり送るが保存しない） |

- ブラウザに置いてよいのは、これまでどおり Supabase の URL と anon キー（公開してよい鍵）だけ。
- コミット前の `scripts/check-secrets.sh` はそのまま使う。

### 3.2 自宅の位置を守る（U-10・D-17）
- 送るのは「候補の店の id（と、地図だけの店は店の位置）」だけ。自宅・現在地・距離・晴れたセルは送らない。
- それでも候補の店はだいたい自宅のまわりに集まるので、**候補の一覧からおおよその地域は推定できる**。これは 2026-11-05 の決定（端末が候補を送る）で受け入れた範囲。被害を小さくするため:
  - Edge Function は候補の一覧を**保存しない・ログに出さない**。保存するのは選んだ最大3件だけ。
  - `daily_hints` に方角・距離の列は作らない（DB 設計 3.10 のとおり）。
  - 候補の数に上限を付け（§11）、端末でランダムに間引いてから送る。

### 3.3 RLS と書き込みの権限
- `daily_hints` は 0001 で作成済み。RLS 有効、読みは**本人の行だけ**（`daily_hints_select_own`）、ブラウザからの書き込みは無し。書くのは Edge Function（service_role）だけ。今回この方針は変えない。
- 新しい SQL 関数（§5）は `security definer`（作った人の権限で動く）で、実行できるのは service_role だけ（anon・authenticated からは実行不可）。0002 の `perform_checkin` と同じ。
- `shops` は authenticated 全員が読める（N-04 の決定「店名は端末の画面で伏せるだけ」）。今回も変えない。

### 3.4 そのほか
- 日の区切りは日本時間0時。サーバーは `checkin/core.ts` の `jstDay`、端末は `src/checkin/domain/day.ts` の `jstDay` を使う（同じ式）。**どの日かを決める正本はサーバー**。
- 完全無料の範囲。`daily-hints` は外部の有料 API を呼ばない（ホットペッパーは呼ばず、`shops` の控えを使う。地図タイルは謎の気配の確認で最大数回だけ）。
- ホットペッパーのクレジット表示: ヒント（キャッチ・予算・ジャンル）はホットペッパー由来なので、探索シートとヒントのシートを開いている間も「Powered by ホットペッパーグルメ Webサービス」が見えること。

## 4. Approaches（考えた作り方と、選んだもの）

### 4.1 気配の選び方
| 案 | 中身 | 良い点 | 困る点 |
|---|---|---|---|
| **A. 端末が候補、サーバーが抽選（採用）** | 端末が「自宅1kmの霧の中の未訪問店」の id を集めて送る。サーバーが本当にあるか・未訪問かを確かめ、ランダムに選んで保存する | 自宅の座標をサーバーに渡さない。抽選と保存がサーバーなので、開き直しても同じ・+10 の判定もサーバーでできる | 候補の一覧からおおよその地域は分かる（受け入れ済み）。「霧の中か」は端末の申告を信じるしかない |
| B. 端末だけで抽選し、結果を保存 | 端末が選んで、サーバーは保存するだけ | 作りが一番簡単 | 端末が好きな店を選べてしまい +10 を自由に取れる。2台の端末で違う気配になりうる |
| C. サーバーが自宅の大まかな位置を知って選ぶ | 自宅の概略位置をサーバーに置き、サーバーが店を探す | 端末の作業が要らない。定期生成もできる | 「自宅の正確な座標は端末内のみ」（S15）と U-10 の決定に反する |

**選んだもの: A**（2026-11-05 本人決定、D-17）。理由は、自宅を守る約束（S15・U-10）と、+10 の不正を防ぐこと（抽選・記録をサーバーで行う）の両方を満たすのが A だけだから。
残る弱点（端末が候補を絞って送れば、近くの店ばかりにできる）は、抽選がランダムでコインも小さい（+10）ため、初版では受け入れる。

### 4.2 気配のピンの出し方
| 案 | 中身 | 判断 |
|---|---|---|
| **HTML マーカー（採用）** | ビルのピン（`src/shops/infra/buildingPins.ts`）と同じ、MapLibre の `Marker` に HTML の部品を載せる | 3つだけなので重さは問題ない。地図の絵の手前に出るので、**雲（自前の WebGL の層）の上に必ず見える**。弾む・ぼかすなどの演出が CSS で簡単。ビルのピンと見た目・作りをそろえられる |
| GeoJSON の層（基本設計の案） | 地図の中の symbol / circle の層で描く | 霧は自前の描画の層なので、層の重ね順の調整が要り、雲の下に隠れやすい。演出も作りにくい |

**基本設計とのずれ**: 基本設計 5 章の表（234行付近）は「お店ピン・気配ピン｜MapLibre の GeoJSON source ＋ symbol/circle layer｜DOM マーカーで大量に置かない」としている。この注意の目的は「**大量に**置くと重い」ことで、気配のピンは1日最大3つなので当てはまらない。しかもお店のピンはすでに HTML マーカー（ビルのピン）で実装済み。よって気配のピンも HTML マーカーにする。基本設計の表は、実装のあとに「気配ピンは3つだけなので HTML マーカー（2026-11-07）」と書き足す（§13 の手順14）。

## 5. データ

### 5.1 テーブル `daily_hints`（0001 で作成済み。形は変えない）
DB 設計 3.10 のとおり。おさらい:

| 列 | 使い方（今回） |
|---|---|
| hint_id | 気配1件の番号 |
| user_id | 誰の気配か |
| hint_date | どの日の気配か（日本時間の日付。サーバーが決める） |
| slot | 1〜3。並び順。1〜2件しか無い日は 1 から詰める |
| shop_id | 行き先の店（`hp:…` か、謎の気配なら `osm:…`）。`shops` に行が要る（外部キー） |
| hint_genre | ホットペッパーのジャンル名そのまま（例「中華」）。画面で「中華？」と出す。謎の気配は NULL |
| hint_catch | キャッチの断片（§6.4）。無ければ NULL |
| hint_budget | 予算帯（§6.4）。無ければ NULL |
| is_mystery | 謎の気配か（このとき hint_genre は NULL。CHECK 済み） |
| completed_checkin_id | この気配の店にチェックインした記録。NULL ＝まだ |

- 一意制約（すでにある）: `(user_id, hint_date, slot)` と `(user_id, hint_date, shop_id)`。同じ日に同じ枠・同じ店は2つ作れない。
- 気配なしの日は**行を作らない**（DB 設計 3.10）。
- 「翌朝リセット」は、翌日の行を作るだけで表す。古い行は消さない（記録に使うため。DB 設計 3.10）。

### 5.2 migration `0004_daily_hints.sql` の中身
表はすでにあるので、0004 で足すのは **SQL 関数2つ**（1つは新規、1つは置き換え）。

**(1) 新規 `create_daily_hints(p_user uuid, p_day date, p_rows jsonb)`**
- 目的: 「その日の気配がまだ無ければ作り、あればそれを返す」を1つのトランザクションで行う。同じ日の二重生成を防ぐ本体。
- 中身の流れ:
  1. `profiles` の本人の行を `FOR UPDATE` で押さえる（同じ人の同時の要求を1つずつ順番に通す。行が無ければ `profile_missing` で止める＝0002 と同じ）。
  2. `daily_hints` に `(p_user, p_day)` の行が1つでもあれば、何も書かずにそれを返す。
  3. 無ければ `p_rows`（`[{slot, shop_id, hint_genre, hint_catch, hint_budget, is_mystery}, …]`、0〜3件）を挿入して返す。
- 戻り値: その日の `daily_hints` の行（slot 順）。
- 権限: `security definer`、`set search_path = ''`、実行は service_role だけ（0002 と同じ書き方で revoke / grant）。
- 一意制約があるので、万一ロックをすり抜けても2組目は DB が止める（二重の守り）。

**(2) 置き換え `perform_checkin`（気配の +10 を組み込む）**
- 0003 の動き（同じ店は1日1回、2回目は `already_today`）はそのまま残す。
- 引数を1つ足す: `p_alt_shop_id text`（合体した店の元の地図の点 `osm:…`。気配の照合にだけ使う。無ければ NULL）。
- 戻り値に `was_hint boolean` を足し、`coins_awarded` は 30 か 40 になる。
- 引数と戻り値の形が変わるので、`create or replace` では置き換えられない。**古い関数を `drop function public.perform_checkin(uuid, text, boolean, date, jsonb)` してから作り直し**、権限（service_role だけ）を付け直す。
- 中身の流れ（足す所に ★）:
  1. プロフィールの確認（今までどおり）。
  2. ★ 今日の気配を探す: `daily_hints` から `user_id = p_user`・`hint_date = p_day`・`shop_id in (p_shop_id, p_alt_shop_id)`・`completed_checkin_id is null` の行を1つ、`FOR UPDATE` で取る。
  3. `checkins` に挿入（★ `was_hint` に「2で見つかったか」を入れる）。今日すでに済みなら `already_today`（今までどおり）。
  4. `coin_ledger` に `checkin` 30（今までどおり）。★ 気配なら `hint_bonus` 10 も入れる（DB 設計どおり2行で記録。金額は CHECK で 10 に固定済み、`(checkin_id, reason)` の一意で二重付与も止まる）。
  5. ★ 気配なら `daily_hints.completed_checkin_id` にこのチェックインを入れる。
  6. 霧のセル（今までどおり）。
  7. 返す: `checkin_id`、`coins_awarded`（30 か 40）、`new_cells`、★ `was_hint`。
- `was_hint` はブラウザの申告ではなく、この関数が `daily_hints` を見て決める（DB 設計 3.5 の注記のとおり）。
- 昨日の気配は `hint_date = p_day` に当たらないので +10 は付かない（翌朝リセットと同じ扱い）。

適用: 開発用 Supabase `mogumo-go-dev` の SQL Editor に貼って Run（0002・0003 と同じ）。本番へ出すときは本番にも流す。

### 5.3 `p_alt_shop_id` が要る理由（端のケース）
地図の店（`osm:`）とホットペッパーの店（`hp:`）は端末で合体する（`src/shops/domain/merge.ts`。合体後の id は `hp:…`、元の点は `mapId`）。候補を集めたときにホットペッパーの読み込みが遅れていると、本当は合体する店が `osm:` だけの店として謎の気配に選ばれることがある。あとで合体すると、チェックインの id は `hp:…` になり、気配の `osm:…` と合わなくなる。
- 対策: チェックインのとき端末は今までどおり `map_id` を送る。`checkin` の Edge Function は、**その `map_id` が今日の未達成の気配の店であるときだけ**、地図タイルでその点がホットペッパーの店から 40m 以内（`MATCH_M`）かを確かめ、通れば `p_alt_shop_id` として渡す。確かめられなければ NULL（+10 なし、チェックイン自体は通る）。
- これで「関係ない `map_id` を送って +10 を取る」ことはできない。
- 加えて、端末はホットペッパーの読み込みが済んでから候補を集める（§7.1）ので、このずれ自体がまれになる。

## 6. Edge Function `daily-hints`（新規）

置き場所: `supabase/functions/daily-hints/`（`index.ts` が Deno の本体、`core.ts` が純粋な計算で Vitest から読む。既存2つと同じ形）。

### 6.1 入力
`POST`、JWT 必須（ユーザーは JWT からだけ決める。既存と同じ確かめ方）。本文:
```
{
  "hp":  ["hp:J001234567", ...],                     // ホットペッパーの情報がある候補の id（最大 HINT_MAX_HP_CANDIDATES）
  "osm": [{ "id": "osm:123", "lat": 35.6, "lng": 139.6 }, ...]  // 地図だけの候補（最大 HINT_MAX_OSM_CANDIDATES）。lat/lng は「店の」位置
}
```
- 形が違う・上限を超える・id の形が `^hp:[A-Za-z0-9]{1,32}$` / `^osm:\d+$` でない → 400。
- 自宅・現在地・距離は受け取らない（項目自体が無い）。

### 6.2 出力
```
200 {
  "hint_date": "2026-11-07",
  "hints": [
    { "hint_id": "...", "slot": 1, "shop_id": "hp:...", "hint_genre": "中華", "hint_catch": "自家製麺の濃厚つけ麺",
      "hint_budget": "1001～1500円", "is_mystery": false, "completed": false,
      "shop": { "name": "…", "lat": 35.6, "lng": 139.6 } },
    ...
  ]
}
```
- `hints` が空 ＝ 今日は気配なし。
- 店名（`shop.name`）も返す（N-04「店名は端末の画面で伏せるだけ（データは届く）」）。端末は 30m までは画面に出さない。
- エラー: 401 unauthorized／400 bad_request／409 profile_missing／500 internal_error。地図タイルが読めないのは謎の気配が出せないだけなので、エラーにせずホットペッパーの店で埋める（§6.3）。
- ログ: 候補の id・位置・ユーザー id・トークンを出さない（既存と同じ方針。`console.error('daily-hints failed')` のような固定の文だけ）。

### 6.3 処理の流れと、同じ日の二重生成の防ぎ方
1. JWT を確かめる。`day = jstDay(new Date())`（サーバーの日付が正本）。
2. **すでに今日の行があれば、それを返して終わり**（候補は見ない）。安い道を先に通す。
3. 候補を確かめる（端末の言うことは信じない）:
   - `hp` 候補: `shops` に行があり、名前がある店だけ残す。ヒントの材料（ジャンル・キャッチ・予算）は**端末から受け取らず `shops` の行から作る**。
   - 未訪問: その人の `checkins` に、候補の `shop_id` があれば外す（`hp` も `osm` も）。
4. 抽選（`core.ts` の純粋な関数。乱数は引数で渡し、テストで固定できるようにする）:
   1. 謎の気配の日か: `random() < HINT_MYSTERY_DAY_RATE`（0.25 ＝ 4日に1回くらい）かつ `osm` 候補がある。
   2. 謎の日なら `hp` から 2件、`osm` から 1件（`HINT_MYSTERY_PER_DAY`）。ふつうの日は `hp` から 3件。どれも重ならないようにランダムに選ぶ。
   3. **候補が足りない日**:
      - `hp` が足りない → 足りない分を `osm`（謎の気配）で埋める（ふつうの日でも）。気配がまったく無い日をなるべく減らすため。※オーナー確認 §15-1
      - 謎の日なのに `osm` が無い → `hp` で3件。
      - それでも合計が3件に届かない → あるだけ（1〜2件）で作る。※オーナー確認 §15-1
      - 合計0件 → 行を作らず `hints: []` を返す（気配なし）。
   4. 枠（slot）はランダムに並べる（謎の気配がいつも3番目にならないように）。
5. 謎の気配に選んだ `osm` の店を確かめる: 地図タイル（OpenFreeMap、`checkin` と同じ読み方）で、**店の位置**のタイルにその番号の「名前のある飲食店の点」があるか。あれば `shops` に upsert（名前・位置・`genre_name` は地図の種類。`checkin` が地図の店を書くときと同じ）。無ければ次の `osm` 候補で試す（最大 `HINT_MYSTERY_VERIFY_TRIES` 回）。だめなら `hp` 候補で埋める。タイルが読めないときも `hp` で埋める。
   - 地図タイルの読み方は今 `checkin/index.ts` の中にある。`supabase/functions/_shared/osmTile.ts` に移して2つの関数で共有する（`checkin` の動きは変えない）。
6. `create_daily_hints(user, day, rows)` を1回呼ぶ（§5.2）。**同時に2回呼ばれても、関数の中のロックと一意制約で1組だけになる**。返ってきた行（先に別の要求が作った分のこともある）に `shops` の名前・位置を付けて返す。
- 二重生成の守りは3段: ①最初に「今日の行があるか」を見る ②SQL 関数が本人の行をロックしてから確かめる ③一意制約 `(user_id, hint_date, slot)`・`(user_id, hint_date, shop_id)`。
- 気配なし（0件）の日は行が無いので、次にアプリを開いたときにもう一度作ろうとする。遠出した日に、出先で気配が出ることになる（S10 の趣旨に合う）。※オーナー確認 §15-6

### 6.4 ヒントの作り方（`core.ts`、`hp` の店だけ）
**ジャンル（あいまい表示）**
- `hint_genre` には `shops.genre_name`（ホットペッパーのジャンル名）をそのまま入れる。画面で後ろに「？」を付けて「中華？」「居酒屋？」と出す。
- ジャンル名が無い `hp` の店は、`hint_genre = NULL` のまま `is_mystery = false`（画面では「ジャンル？」とだけ出す）。謎の気配は地図だけの店に限る（オーナー決定）。

**キャッチの断片**（S5「キャッチコピーの断片」）
1. キャッチが無ければ NULL。
2. 【 】［ ］《 》≪ ≫ などのかっこを中身ごと消す（駅からの道のりや宣伝が入りやすい）。
3. 区切り（`。！!？?♪☆★◆◇■□●○／/、,…` と空白・改行）で短い切れ端に分ける。
4. 外す切れ端: **店名を含むもの**（名前の比べ方は `src/shops/domain/merge.ts` の `normalizeName` と同じならし方。サーバー側に同じ式を写し、`keep in sync` と書く）、「駅」「徒歩」を含むもの、3文字以下のもの。
5. 残りの最初の切れ端を使う。`HINT_CATCH_MAX_CHARS`（14文字）を超えたら切って「…」を付ける。
6. 残らなければ NULL。
- 画面では「…自家製麺の濃厚つけ麺…」のように前後に「…」を付けて「断片」らしく見せる。
- 店名がカタカナと漢字で書き分けられているなど、完全には消しきれない場合がある（初版の割り切り）。

**予算帯**
- `hint_budget` には `shops.budget_name`（ホットペッパーの予算の帯の名前。例「1001～1500円」）をそのまま入れる。すでに帯なので、新しい区切りは作らない。※オーナー確認 §15-5

**謎の気配**
- `hint_genre`・`hint_catch`・`hint_budget` はすべて NULL、`is_mystery = true`。

## 7. 端末側

### 7.1 候補の集め方（`src/hints/domain/candidates.ts`、純粋な関数）
材料は、地図がすでに持っている情報だけ（新しい問い合わせはしない）:
- `shops`: 合体済みのお店の一覧（`worldLayers` の `shops`。今いる場所のまわり 1km の分）
- `cleared`: 晴れたセル（自宅 200m＋サーバーのセル＋今後ルート）
- `checked`: 済みの店 id（合体した店は地図の点の id でも済み。`worldLayers` の `checkedNow`）
- `home`（端末の自宅）、`me`（今の位置）

ルール:
1. **範囲**
   - 自宅から `HINT_HOME_RADIUS_M`（1km）以内にいる → 自宅から 1km 以内の店。
   - 自宅の範囲の外にいる → 自宅から 1km 以内の店 **と** 今いる場所から `HINT_AWAY_RADIUS_M`（1km）以内の店（S10「今いる場所の周りからも」）。
   - 自宅が無い（ふつうは起きない）→ 今いる場所のまわりだけ。
   - 注意: 読み込んでいる店は「今いる場所のまわり 1km」なので、自宅の範囲でも今いる場所から遠い側の店は候補に入らない。自宅を中心に店を問い合わせると自宅の位置をサーバーに教えることになるので、**わざわざ取りに行かない**（割り切り）。
2. **霧の中**: 店の位置のセルが晴れていない（`isClearedAt(cleared, shop)` が false）。
3. **未訪問**: `checked` に無い（`id` でも `mapId` でも）。
4. **名前がある**（S9: 名前が無い店は対象外）。
5. 振り分け: `id` が `hp:` で始まる → `hp` 候補（id だけ送る）。`osm:` で `details` が無い → `osm` 候補（id と店の位置）。
6. 上限を超えたらランダムに間引く（乱数は引数）。

**いつ集めるか**
- 「ホットペッパーの読み込みが1回成功」「地図のお店の取り出しが済んだ」「保存済みの進み具合（`loadProgress`）の読み込みが済んだ」の3つがそろったら。`worldLayers` に「そろった」を知らせる口を足す（§9）。
- ホットペッパーが使えない環境（`shopSourceEnabled` が false。今の本番）では気配を作らない（謎の気配だけの日になってしまうため）。
- `HINT_READY_TIMEOUT_MS`（30秒）待ってもそろわなければ、探索シートは「いまは気配を探せません。少し歩いてから開き直してね」（仮の文）にする。そろった時点で続きを行う。

### 7.2 送る情報の最小化
- 送る: `hp` の id の一覧、`osm` の id と店の位置の一覧。
- 送らない: 自宅、現在地、距離、方角、晴れたセル、自宅の範囲の内か外か。
- `daily-hints` の呼び出しは**その日に今日の行が無いときだけ**（毎回は送らない）。

### 7.3 流れ（`src/hints/ui/useDailyHints.ts`）
1. ログイン後、地図を開いたら、まず `daily_hints` を直接読む（RLS で本人の行だけ）。`hint_date = jstDay(今)`、`shops(name, lat, lng)` を一緒に読む。
2. 行があれば表示して終わり。
3. 無ければ、§7.1 の「そろった」を待って候補を集め、`daily-hints` を呼ぶ。返ってきた `hint_date` と行を使う（端末の時計がずれていてもサーバーの日付に従う）。
4. 届くまで探索シートは「気配を探しています…」（D-17）。地図は待たせない。
5. 失敗（通信など）→ 「気配を読み込めませんでした」＋「もう一度」ボタン。自動のやり直しは1回だけ。
6. **日付の切り替わり**: 画面が前に戻ったとき（`visibilitychange`）と、`HINT_DAY_CHECK_MS`（1分）ごとに `jstDay` を見て、変わっていたら気配を消して 1 からやり直す。
7. チェックインの結果 `was_hint = true` が返ったら、その気配を「達成」にする（読み直さずに手元で更新）。

### 7.4 店名を明かす（30m）
- `src/hints/domain/reveal.ts`: 今の位置（ならした位置。`MapView` が `onPosition` で渡すもの）と気配の店の距離が `HINT_REVEAL_M`（30m）以内なら「明かす」。
- 一度明かしたら、その日は明かしたまま（GPS のぶれで伏せ直さない）。明かした気配の id は localStorage `mogumo.hintsRevealed.<userId>` に `{ day, ids }` で持つ（自宅とは関係ない情報なので端末に置いてよい）。日付が変われば捨てる。
- 気配の店にチェックインしたら（`completed`）、30m に入っていなくても明かした扱いにする。
- 店の位置は、端末の合体済みの店があればその位置（地図の点）、無ければ `shops` の位置。ピンの位置も同じ。

### 7.5 他の画面で店名を伏せる
霧の中でも 50m 以内の店は建物が見え（`IN_FOG_VISIBLE_M`）、押すとお店のシートが開く。30m より外でも店名が出てしまうので:
- お店のシート（`ShopSheet`）とビルの一覧（`BuildingSheet`）は、**今日のまだ明かしていない気配の店**なら、店名を「？？？」にする。キャッチ・予算などホットペッパーの詳細も、ヒントと同じ出し方にそろえる。
- チェックインは 50m のまま押せる（S5「チェックイン可能距離（50m）とは別ルール」）。30m より前にチェックインした場合は、チェックインの演出で店名を明かす。※オーナー確認 §15-4

## 10. テストの方針

- **domain（中心）**
  - `candidates`: 自宅の範囲の内／外、霧の中だけ、晴れた店は外れる、済み（id・mapId）は外れる、名前なしは外れる、`hp`・`osm` の振り分け、上限で間引く（乱数を固定）。
  - `hint`: 「中華？」、ジャンル無し、謎の気配の文、断片に「…」、予算そのまま。
  - `reveal`: 30m ちょうど・31m、一度明かしたら離れても明かしたまま、達成で明かす。
- **サーバーの core（Vitest で `core.ts` だけ読む。既存と同じ）**
  - 入力の確かめ（形・上限・id の形）。
  - 抽選: ふつうの日は hp 3件、謎の日は hp 2＋osm 1、hp 不足を osm で埋める、謎の日に osm 無し、合計1〜2件、0件、重複なし、slot が 1 から詰まる（乱数を固定）。
  - キャッチの断片: かっこを消す、店名入りを外す、駅・徒歩を外す、14文字で切る、残らないと NULL。
  - `osmTile` を `_shared` に移したあとも `checkin` の既存テストが通ること。
- **infra**: `hintsApi` の返事の読み取り（壊れた形は捨てる、40 と `was_hint`）、時間切れ、`revealStore` の日付の切り替え。`hintPins` は作る・入れ替える・消すの最小限（MapLibre はモック。ビルのピンのテストにならう）。
- **ui（Testing Library）**: 探索シートの5つの状態（読み込み中・3件・達成あり・気配なし・失敗）、ヒントのシートに店名が出ないこと、お店のシート・ビルの一覧で伏せること、明かしの帯。
- **DB（手で確かめる。開発用 Supabase）**: 同じ日に2回作っても1組、同時に2回呼んでも1組、気配の店へのチェックインで 30＋10 の2行・`was_hint = true`・`completed_checkin_id` が入る、気配でない店は 30 だけ、昨日の気配の店は 30 だけ、他人の `daily_hints` は読めない、authenticated から関数を実行できない。
- 全体: `npm test`・`npx tsc -b`・`npm run lint`・`npm run build`。

## 15. オーナーに確認が要る点
1. **候補が足りない日**: ホットペッパーの店が3件に足りないとき、足りない分を「謎の気配」で埋めてよいか（その日は「たまに」より多く謎が出る）。それでも足りなければ、気配が1〜2件だけの日があってよいか（SPEC は「毎日3件」）。
2. **謎の気配の割合**: 「4日に1回くらい、3件のうち1件」（リーダーの判断）でよいか。
3. **気配なしの日の案内**: 「近くの未訪問店を通常ピンで案内」を、探索シートに近い順で3件の名前を並べ、押すとカメラが移動する形にしてよいか。件数は3でよいか。
4. **30m より前のチェックイン**: チェックインは 50m からできる（別ルール）ので、30〜50m の間でチェックインすると、店名を伏せたままチェックイン → 演出で正体が分かる、という流れになる。これでよいか。
5. **予算の出し方**: ホットペッパーの予算の書き方そのまま（例「1001～1500円」）でよいか。
6. **気配なしの日の作り直し**: 気配が0件だった日は、アプリを開き直すたびにもう一度作ろうとする（遠出した日は、出先で気配が出ることがある）。「生成は1日1回」の決定と少し違うが、これでよいか。
7. **距離・方角の表示**: ヒントに「ここから約 400m」や方角を出すか（SPEC §2.4 の例にはあるが決定ではない。今回は出さない）。
8. **「今日は気配なし」の絵**: シロに頼むか、まずは文字だけでよいか（頼むならキャラはだれにするか）。
