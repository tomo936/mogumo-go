  - 3D（試作）: `src/map/infra/avatarModel.ts` と `src/map/domain/avatar3d.ts`。`src/assets/characters/avatar3d.glb`（約 0.9MB、立ち絵から Hunyuan3D-2 で作った。骨組み（リグ）なし・揺れるだけ）。読めたら 2D を隠して出す。
- 立ち絵: `src/assets/characters/starter-boy.webp`・`starter-girl.webp`。**男の子は地図を持っている絵**。オーナーは「アバターが地図を持っているのは消してもいいかも」と言っている（地図の上を歩くので。持たせない方向で作ってよい）。

- 使える道具（PC 側、オーナーの Windows）: ComfyUI ＋ Hunyuan3D-2（`D:\mogumo-3d`、RTX 3060 12GB、`comfy-mcp` が登録済み）、Blender（`art/prototypes/` に手順）。`handoff/to-claude/2026-11-09-avatar-3d-trial.md` に3D化の経緯と調査メモ（ライセンス、Mixamo の候補）がある。
- 画像・動画の素材は `handoff/to-shiro/` に依頼ファイルを書いてミシェーラ（画像担当の別エージェント）に頼む決まり。コードで描ける絵（SVG・シェーダ）は自分で作ってよい。

## 2. 条件（動かさない）
- 完全無料の範囲。有料のサービス・課金が要る道具は使わない。
- iPhone で軽く動く。地図（MapLibre）・お店の3D・雲の WebGL と同時に動くので、**追加の重さは実測して数字で報告**する（読み込みの大きさ・1コマの時間・メモリ）。目安: アバター1体のファイルは 1MB 以内、キャラが増えても最初の読み込みを増やさない（使うキャラだけ遅れて読む）。
- 画面での大きさは、普段の寄り（今の標準のズーム）で今と同じくらい（高さ 40px 前後）。ただし**小さくても表情が分かる**ことが今回の目的。
- **大きさは、画面ではなく地図の上で固定**（オーナー 2026-11-11: 「今巨人化してるから、サイズは視点を変えても固定にしたい」「引いた時デカすぎる。一緒についてくる」＋スクリーンショット）。今の 3D は、画面の高さ（`AVATAR_HEIGHT_PX = 40`）を保つようにズームで大きさを変えているので、**地図を引くとお店や建物に比べて巨人になる**（画面は引いても、アバターの大きさは変わらずについてくる）。直す向き: アバターを**実際の物の大きさ（地図の上の m）で固定**し、引けばお店と同じ割合で小さくなり、寄れば大きくなる（お店の模型と同じ扱い）。ただし小さくなりすぎて見えなくならないよう、画面での最小の高さ（案: 16px 前後）は決めてよい。値（実際の大きさ・最小の高さ）は設計メモで提案し、傾き（ピッチ）・ズーム・チェックインのカメラの寄せでも、お店との大きさの割合が変わらないことを実装のテストと画像（引いた図・寄った図）で示す。`src/map/domain/avatar3d.ts` の `heightMeters`（画面の高さから m を出している）が今の原因。
- **見た目の質（オーナー 2026-11-11: 「今の3Dはざらついてるし、色の塗り方も雑だから改善してほしい」）**。今の `avatar3d.glb` は、立ち絵から AI で作ったままで、表面がざらつき（ノイズ・低い解像度の色）、色の塗りも荒い。新しいアバターでは、①表面がなめらか（輪郭がギザギザしない・色がにじまない・小さく表示してもざらつかない）、②色が立ち絵に近く、塗りが均一で丁寧、③お店の模型・絵本風の地図の色になじむ、を満たす。方式の比較（仕事1）でも「見た目の質」を比べる項目にし、試作の画像（今のものとの並べ）で示す。
- 地図の上の他の物（ピン・雲・自宅）の邪魔をしない。向き・速さの切り替えは今の仕組み（`avatar.ts` の `facingFor`・`isWalking`・`smoothSpeed`）を活かす。
- 安全: 新しい導入物（ソフト・モデル・ライブラリ）は、出所と安全の根拠を確かめてから入れる。PC に入れるものは**入れる前にオーナーに確認**する（過去の許可は、その時のものだけ）。ライセンスは商用可・再配布可を確かめて、メモに書く。
- ルール: 設計に無い判断は勝手に決めず止めて報告する。頼まれていない書き換えをしない。APIキーをソースに書かない・`.env` は読まない。最後に `npm test`・`npx tsc -b`・`npm run lint`（warning は基準の 33 件）を通す。同じ方法で2回失敗したら、別の方法に切り替えるか、先に実測して前提を確かめる。それでも進まなければ止めて報告する。
- クリーンアーキテクチャ（`CLAUDE.md`）: domain は純粋な計算、infra は外とのつなぎ、ui は画面。ブラウザ・three.js の API を domain に入れない。

## 3. 仕事1: 各キャラの実装の方針（設計メモ）
書き出し先: `docs/superpowers/specs/2026-11-11-avatar-design.md`。次を、**数字つきで**書く。
1. **方式の比較と推し**: 2D コマ絵（今）／3D モデル＋骨組み＋表情（モーフ・顔の差し替え）／Live2D（SPEC にポコタンの案あり。ライセンスと重さを確認）／そのほか見つけたもの。表情・向き・歩き走り・キャラの増やしやすさ・iPhone での重さ・無料で回るか・作る手間（オーナーは自分でツールを触らない。エージェントだけで回ること）で表にする。可能なものは小さく試作して**実測**してから推す。
2. **キャラの作り方の流れ**: 立ち絵 1 枚（ミシェーラの絵）から、地図で使う動くキャラにするまでの手順と、1 キャラあたりの手間・容量。最初の2人（男の子・女の子）と、ガチャで増えるキャラ（動物など人型でないものも含む）の両方で成り立つか。人型でない（クッキーくまなど）の扱い。
3. **表情の設計**: 最低限の種類（案: ふつう・うれしい・びっくり・おいしい・ねむい など）と、いつ出すか（案: チェックイン完了・Lv アップ・町クリア・ミッション達成・気配に近づいた・長く止まっている）。小さい画面（高さ 40px）でも見分けられる作り方。
4. **動きの設計**: 待機・歩き・走りの切り替え、向きの扱い（3D なら実際に回す／2D なら何方向）、止まる・動き出すときのつなぎ、チェックインの演出で入口まで歩く案（SPEC の 2026-11-09 の案。今回は設計だけ、実装は別）。
5. **ミシェーラに頼む素材の一覧**（あれば）。仕様（内容・サイズ・用途・画風）を書いた依頼ファイルを `handoff/to-shiro/YYYY-MM-DD-<slug>.md` に作る（先頭に `状態: 未対応`）。
6. **PC に入れるものの一覧**（あれば）と、その安全の根拠・ライセンス。
7. **オーナーに聞くこと**（決め切れない点。推奨案つき）。

## 4. 仕事2: 表情つきで動くアバターの実装（メモに OK が出てから）
- 対象: まず男の子と女の子（最初の2人）。**自分の位置に出る、実際に動くアバター**。待機・歩き・走り、進む向きに合わせた向き、表情の切り替え（最低 3 種類）。
- 表情の切り替えは `MapView`／`MapPage` から呼べる小さな窓口にする（例: `avatar.express('happy')`）。実際の呼び出し（チェックイン完了で うれしい など）まで今回つなぐ。
- 地図を持たせない（上記）。
- 今の 2D・3D 試作は、新しいものが読めないときの代わりとして残すか、置き換えて消すかを、メモで決めて報告する。
- 大きさの固定と、ざらつき・塗りの改善（上の条件）を満たすこと。
- テスト: 純粋な計算は単体テスト。見た目は、スマホ幅（390px）の画像で、待機・歩き・走り・各表情を並べて確認し、オーナーに PNG で見せる。重さの実測（4 の条件）を報告に入れる。
- 終わりの報告: 変えたファイル、実測した数字、オーナーに見てもらう点（iPhone 実機）、残した課題。
