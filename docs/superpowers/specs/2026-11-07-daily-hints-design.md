# 設計: 気配・デイリー（今日の気配3件）

日付: 2026-11-07。設計役が作成し、同じ日にオーナーの回答とリーダーの判断で仕上げた（§15）。前の段は `2026-11-06-hotpepper-checkin-design.md`（チェックイン）と `2026-11-07-shop-lod-design.md`（お店を全部出す）。
この段はコードを書く前の設計メモ。実装は実装役が行う。

用語の言いかえ（このメモで使うもの）
- **Edge Function**: Supabase の上で動く、サーバー側の小さなプログラム。秘密の鍵はここでだけ使える。
- **RLS**: DB の「行ごとの読み書きの許可」。本人の行しか読めない、などを DB 自身が守る。
- **migration（マイグレーション）**: DB の形を変える手順書（SQL のファイル）。番号順に流す。
- **トランザクション**: 「全部成功するか、全部取り消すか」のひとまとまりの書き込み。
- **SQL 関数**: DB の中に置いた手続き。Edge Function から1回呼ぶと、中身が1つのトランザクションで動く。
- **一意制約**: 「同じ組み合わせの行を2つ作れない」という DB の決まり。二重登録を DB が止める。
- **HTML マーカー**: 地図の上に重ねて置く、ふつうの画面部品（ボタンなど）。地図の絵の中ではなく、その手前に出る。
- **世代（generation）**: その日の気配の「何組目か」。最初が 1、「この辺りで探し直す」で作り直すと 2。
- **domain / infra / ui**: CLAUDE.md の3つの置き場所（決まりと計算／外とのつなぎ／画面）。

## 1. 意図と理由

- SPEC S4 で、デイリークエストは「**毎日3件、すべて『気配』型**。行き先は霧の中の未訪問店で、店名は伏せ、気配（ヒント）だけを出す。利用者は3件から選んで行く」と決まっている。案B（霧の向こうのお題）の芯で、「まだ行ったことのない店へ行く理由」を毎日つくるのがねらい。
- ここまでで、地図・霧・お店・チェックインがそろった。気配はこれらを組み合わせるだけで作れる段階にある。次の図鑑（未訪問カードは「気配と同じ出し方」S11）にも、ここで作るヒントの出し方がそのまま使える。
- 決め方の根拠（正本の引用）
  - S5: 「気配は **霧（モヤ）の中にピンが刺さった形** で地図に出す。ピンには店名を出さず、**曖昧な特徴を少しだけ**出す（例: ジャンルを『中華？』と曖昧に、その店の個性を少し）。**気配をタップするとカメラがその場所へ移動する**。店名が明かされるのは **店から 30m 以内**」。「ジャンルが分からない店は **たまに出る『謎の気配』枠**」。「個性ヒントの材料は **お店のキャッチコピーの断片＋予算帯の両方**」。
  - S10: 「デイリーの気配は、**自宅の範囲の外にいる時は今いる場所の周りからも出す**」。
  - S15: 「選ばなかった気配は翌朝リセット。気配の店が無い日は『今日は気配なし』表示＋近くの未訪問店を通常ピンで案内」。
  - S16: 「気配ピン（霧の中）は…アイコンに『？』を重ねてぼかした表示にする」。
  - S17: 「下部中央に大きな丸ボタン『探索』を置き、タップで探索シートが開く。探索シートの中身は、今日の気配3件／週ミッションの進捗／図鑑・記録・マイページへの入口」。
  - §9（2026-11-05）: 「**気配は『端末が候補、サーバーが抽選』**: 端末が自宅1kmの霧の中の未訪問店（圏外では現在地周りも）の候補を送り、サーバーがランダムに3件選ぶ。生成はその日に初めてアプリを開いたときの1回。気配の店名は端末の画面で伏せるだけ（D-17、U-10、N-04）」。→ 生成の時は 2026-11-07 のオーナー決定で「その日初めて探索シートを開いたとき」に変更（下）。
  - §8・§9: コインは「チェックイン30／気配の店はボーナス+10で40」。「同じ店のコインは1日1回まで（D-15）」。さらに 2026-11-07 本人決定で「**同じ店のチェックインは1日1回まで**…日の区切りは JST 0時」。
  - DB 設計 3.10・D-17・D-19、基本設計 6.2・U-10・N-04。
- 2026-11-07 のオーナー決定（今回の会話の正本）
  - 気配の対象は、基本は**ホットペッパーの情報（キャッチ・予算・ジャンル）がある店**（`hp:` を持つ店）。地図データだけの店（`osm:` だけ）は「謎の気配」として**たまに**混ぜる。
  - 気配のピンは **HTML マーカー**（ビルのピンと同じ方式。雲の上に見える）。
  - 自宅の外で気配が作られる日があることは受け入れる（§7.1）。そのかわり、作る時を3つ工夫する: **(a) その日初めて探索シートを開いたときに作る (b) 速く動いている間（時速15km 超）は作らない (c) 今日の気配から 1.5km 以上離れていて、まだ1件も達成していなければ「この辺りで探し直す」（1日1回、回数はサーバーが数える）**。
  - 本番（main）にはまだ出さない。今回は開発用 `mogumo-go-dev` だけで動けばよい。
- リーダーの判断は §15 にまとめた（本文の該当箇所にも「リーダーの判断」と書いた）。

## 2. 目標・しないこと・失敗とみなすこと

### 目標（今回やること）
1. 地図の下の真ん中に大きな丸い「探索」ボタン。押すと探索シートが開く。シートの中身は **今日の気配3件だけ**。
2. 今日の気配の生成: その日（日本時間）に初めて**探索シートを開いた**とき、端末が候補を集めて送り、サーバーが3件を抽選して保存する。2回目以降は保存したものを読むだけ。速く動いている間は作らない。
3. 「この辺りで探し直す」: 今日の気配から 1.5km 以上離れていて、まだ1件も達成していなければ、1日1回だけ今いる場所のまわりで作り直せる。
4. 気配のピン: 霧の中の店の位置に、仮の丸＋「？」の HTML マーカー。シロのアイコン13種が届いたら差し替える。
5. ピン（または探索シートの気配）を押すと、カメラがその場所へ移動し、ヒントのシートが開く（店名は伏せる。「ここから 約400m」の距離は出す）。
6. 店から 30m 以内に入ったら店名を明かす。まずは簡単な演出（ピンがぽんと弾む＋帯で店名）。
7. 気配の店にチェックインしたら +10（合計40）。`checkins.was_hint = true`、`daily_hints.completed_checkin_id` に記録。
8. 翌朝（日本時間0時）リセット: 日付が変わったら昨日の気配は消え、次に探索シートを開いたとき新しい気配を作る。
9. 気配なしの日の表示: 「今日は気配なし」＋近くの未訪問店3件の案内（文字だけ）。
10. 地図にもともと出ている店名の文字で、気配の店名がばれないようにする（§7.6）。

### しないこと（次の段以降・範囲外）
- 週ミッション（探索シートの「週ミッションの進捗」欄も今回は出さない）
- 探索シートの図鑑・記録・マイページへの入口（画面がまだ無い）
- 気配の方角の表示（リーダーの判断で出さない。距離だけ出す）
- シロのアイコン13種への差し替え（届いてから）
- 気配の選び直し（「この辺りで探し直す」以外）・追加・通知
- 気配の店の詳しい画面（N-04 の決定どおり、伏せた状態のヒントのシートだけ）
- 「今日は気配なし」の絵（リーダーの判断で文字だけ）
- **本番（main）の準備**: ホットペッパーを本番で使えるようにすること（今の本番は `shopSourceEnabled` で止めている）、本番の Supabase への SQL 0004・関数 `daily-hints`／新しい `checkin` の反映。今回は開発用 `mogumo-go-dev` だけ（オーナー決定 2026-11-07）

### 失敗とみなすこと
- 店名が、30m に入る前（またはチェックインする前）に画面のどこかに出る（探索シート・ヒントのシート・お店のシート・ビルの一覧・ピン・**地図にもともとある店名の文字**）。
- 自宅の座標や現在地がサーバーに送られる、または Edge Function のログに出る。
- 同じ日に、作り直し以外で気配が2組できる。アプリを開き直すと気配が変わる。作り直しが1日2回以上できる。
- 気配の店にチェックインして +10 が付かない、2回付く、気配でない店に付く、昨日の気配や作り直す前の気配の店で付く。
- 日本時間0時を過ぎても昨日の気配が出たまま。
- 電車・車で移動中に、通り過ぎた町の気配が作られる。
- 気配の取得を待って地図の表示が遅れる（D-17「地図表示は待たせず裏で取得」）。
- iPhone で目に見えて重くなる。

## 3. 制約（非機能要件）

### 3.1 秘密情報（どこで持ち、どこへ出さないか）
| 秘密 | 持つ場所 | 出してはいけない場所 |
|---|---|---|
| `HOTPEPPER_API_KEY` | Supabase の Secrets。読むのは `shops-hotpepper` だけ | ブラウザのコード、`.env` の `VITE_` で始まる値、ログ、`daily-hints`（今回の関数はホットペッパーに問い合わせないので、鍵は**不要**） |
| `SUPABASE_SERVICE_ROLE_KEY`（何でも書ける強い鍵） | Edge Function の環境変数（`daily-hints`・`checkin`・`shops-hotpepper`） | ブラウザのコード・ログ・返す値 |
| 利用者のトークン（JWT） | ブラウザ（Supabase のログイン状態）→ 要求のヘッダー | ログ |
| **自宅の座標** | 端末の localStorage `mogumo.home.<userId>` だけ | サーバーへの要求・DB・ログ・URL。**自宅からの距離・方角も送らない** |
| 現在地・速さ | 端末だけ | `daily-hints` には送らない（`checkin` は 50m 判定のため従来どおり送るが保存しない）。「速いか」「1.5km 離れたか」も端末で判断し、送らない |

- ブラウザに置いてよいのは、これまでどおり Supabase の URL と anon キー（公開してよい鍵）だけ。
- コミット前の `scripts/check-secrets.sh` はそのまま使う。

### 3.2 自宅の位置を守る（U-10・D-17）
- 送るのは「候補の店の id（と、地図だけの店は店の位置）」と「作り直しかどうか」だけ。自宅・現在地・距離・速さ・晴れたセルは送らない。
- それでも候補の店は「作った時にいた場所」のまわりに集まるので、**候補の一覧からおおよその地域は推定できる**。これは 2026-11-05 の決定（端末が候補を送る）で受け入れた範囲。被害を小さくするため:
  - Edge Function は候補の一覧を**保存しない・ログに出さない**。保存するのは選んだ最大3件（作り直しがあれば最大6件）だけ。
  - `daily_hints` に方角・距離の列は作らない（DB 設計 3.10 のとおり）。「ここから 約400m」は端末が計算して出すだけ。
  - 候補の数に上限を付け（§11）、端末でランダムに間引いてから送る。

### 3.3 RLS と書き込みの権限
- `daily_hints` は 0001 で作成済み。RLS 有効、読みは**本人の行だけ**（`daily_hints_select_own`）、ブラウザからの書き込みは無し。書くのは Edge Function（service_role）だけ。今回この方針は変えない（0004 で足す列 `generation` も同じ扱い）。
- 新しい SQL 関数（§5）は `security definer`（作った人の権限で動く）で、実行できるのは service_role だけ（anon・authenticated からは実行不可）。0002 の `perform_checkin` と同じ。
- `shops` は authenticated 全員が読める（N-04 の決定「店名は端末の画面で伏せるだけ」）。今回も変えない。

### 3.4 そのほか
- 日の区切りは日本時間0時。サーバーは `checkin/core.ts` の `jstDay`、端末は `src/checkin/domain/day.ts` の `jstDay` を使う（同じ式）。**どの日かを決める正本はサーバー**。
- 完全無料の範囲。`daily-hints` は外部の有料 API を呼ばない（ホットペッパーは呼ばず、`shops` の控えを使う。地図タイルは謎の気配の確認で最大数回だけ）。
- ホットペッパーのクレジット表示: ヒント（キャッチ・予算・ジャンル）はホットペッパー由来なので、探索シートとヒントのシートを開いている間も「Powered by ホットペッパーグルメ Webサービス」が見えること。
- 動かす場所は開発用 `mogumo-go-dev`（localhost と `mogumo-go-dev.vercel.app`）だけ。本番では `shopSourceEnabled` が false なので、探索シートは「いまは気配を探せません」のまま（§7.3）。

## 4. Approaches（考えた作り方と、選んだもの）

### 4.1 気配の選び方
| 案 | 中身 | 良い点 | 困る点 |
|---|---|---|---|
| **A. 端末が候補、サーバーが抽選（採用）** | 端末が「霧の中の未訪問店」の id を集めて送る。サーバーが本当にあるか・未訪問かを確かめ、ランダムに選んで保存する | 自宅の座標をサーバーに渡さない。抽選と保存がサーバーなので、開き直しても同じ・+10 の判定もサーバーでできる。作り直しの回数もサーバーが数えられる | 候補の一覧からおおよその地域は分かる（受け入れ済み）。「霧の中か」は端末の申告を信じるしかない |
| B. 端末だけで抽選し、結果を保存 | 端末が選んで、サーバーは保存するだけ | 作りが一番簡単 | 端末が好きな店を選べてしまい +10 を自由に取れる。2台の端末で違う気配になりうる |
| C. サーバーが自宅の大まかな位置を知って選ぶ | 自宅の概略位置をサーバーに置き、サーバーが店を探す | 端末の作業が要らない。定期生成もできる | 「自宅の正確な座標は端末内のみ」（S15）と U-10 の決定に反する |

**選んだもの: A**（2026-11-05 本人決定、D-17）。理由は、自宅を守る約束（S15・U-10）と、+10 の不正を防ぐこと（抽選・記録をサーバーで行う）の両方を満たすのが A だけだから。
残る弱点（端末が候補を絞って送れば、近くの店ばかりにできる）は、抽選がランダムでコインも小さい（+10）ため、初版では受け入れる。

### 4.2 いつ作るか（オーナー決定 2026-11-07）
| 案 | 判断 |
|---|---|
| アプリを開いたとき（§9 の当初の決定） | 開いた場所が駅や出先だと、そこで1日分が決まってしまう |
| **その日初めて探索シートを開いたとき＋速い間は作らない＋1.5km 離れたら1回だけ作り直せる（採用）** | 「気配を見たい」と思った時・場所で作るので、行ける場所の気配になりやすい。電車の中で通り過ぎる町の気配にならない。出先で別の町へ移ったときの逃げ道もある |

### 4.3 気配のピンの出し方
| 案 | 中身 | 判断 |
|---|---|---|
| **HTML マーカー（採用）** | ビルのピン（`src/shops/infra/buildingPins.ts`）と同じ、MapLibre の `Marker` に HTML の部品を載せる | 3つだけなので重さは問題ない。地図の絵の手前に出るので、**雲（自前の WebGL の層）の上に必ず見える**。弾む・ぼかすなどの演出が CSS で簡単。ビルのピンと見た目・作りをそろえられる |
| GeoJSON の層（基本設計の案） | 地図の中の symbol / circle の層で描く | 霧は自前の描画の層なので、層の重ね順の調整が要り、雲の下に隠れやすい。演出も作りにくい |

**基本設計とのずれ**: 基本設計 5 章の表（234行付近）は「お店ピン・気配ピン｜MapLibre の GeoJSON source ＋ symbol/circle layer｜DOM マーカーで大量に置かない」としている。この注意の目的は「**大量に**置くと重い」ことで、気配のピンは最大3つなので当てはまらない。しかもお店のピンはすでに HTML マーカー（ビルのピン）で実装済み。よって気配のピンも HTML マーカーにする。基本設計の表は、実装のあとに「気配ピンは3つだけなので HTML マーカー（2026-11-07）」と書き足す（§13 の手順16）。

## 5. データ

### 5.1 テーブル `daily_hints`（0001 で作成済み。0004 で列を1つ足す）
DB 設計 3.10 のとおり。今回の使い方:

| 列 | 使い方（今回） |
|---|---|
| hint_id | 気配1件の番号 |
| user_id | 誰の気配か |
| hint_date | どの日の気配か（日本時間の日付。サーバーが決める） |
| **generation（0004 で追加）** | その日の何組目か。最初が 1、作り直しが 2。`smallint not null default 1`、`CHECK (generation between 1 and 2)`（作り直しは1日1回。オーナー決定） |
| slot | 1〜3。並び順。1〜2件しか無い日は 1 から詰める |
| shop_id | 行き先の店（`hp:…` か、謎の気配なら `osm:…`）。`shops` に行が要る（外部キー） |
| hint_genre | ホットペッパーのジャンル名そのまま（例「中華」）。画面で「中華？」と出す。謎の気配は NULL |
| hint_catch | キャッチの断片（§6.4）。無ければ NULL |
| hint_budget | 予算を短く言いかえたもの（§6.4。例「1,000円台」）。無ければ NULL |
| is_mystery | 謎の気配か（このとき hint_genre は NULL。CHECK 済み） |
| completed_checkin_id | この気配の店にチェックインした記録。NULL ＝まだ |

- **今の気配** ＝ その日の行のうち、`generation` が一番大きい組。画面に出すのも、+10 の対象もこの組だけ。
- **作り直す前の組（generation 1）の行は消さずに残す**。理由: DB 設計 3.10「古い行は消さずに残す。達成したクエスト数の記録に使うため」に合わせる。作り直しは「1件も達成していない」ときだけできるので、残る古い組は必ず全部「未達成」で、記録の数がずれることはない。
- 一意制約は0004で付けかえる: `(user_id, hint_date, slot)` → **`(user_id, hint_date, generation, slot)`**、`(user_id, hint_date, shop_id)` → **`(user_id, hint_date, generation, shop_id)`**（作り直した組に、前の組と同じ店が入ってもよい）。
- 気配なしの日（0件）は**行を作らない**（DB 設計 3.10）。作り直しで0件だったときは、前の組をそのまま残し、回数も使わない（§6.3）。
- 「翌朝リセット」は、翌日の行を作るだけで表す。

### 5.2 migration `0004_daily_hints.sql` の中身
1. **`daily_hints` に `generation` を足す**: 列の追加、CHECK、一意制約2つの付けかえ（古い制約名は 0001 の自動の名前。作る人が `\d daily_hints` 等で確かめてから drop する）。
2. **新規 `create_daily_hints(p_user uuid, p_day date, p_regen boolean, p_rows jsonb)`**
   - 目的: 「その日の気配がまだ無ければ作る／あれば返す」と「作り直し」を1つのトランザクションで行う。同じ日の二重生成と、作り直しの回数を守る本体。
   - 流れ:
     1. `profiles` の本人の行を `FOR UPDATE` で押さえる（同じ人の同時の要求を1つずつ順番に通す。行が無ければ `profile_missing` で止める＝0002 と同じ）。
     2. その日の一番大きい `generation` を見る（行が無ければ 0）。
     3. `p_regen = false` のとき: 0 なら `p_rows` を generation 1 で挿入して返す。1 以上ならその組を返す（何も書かない）。
     4. `p_regen = true` のとき: 0 なら `no_hints`、2 なら `regen_used`、今の組に `completed_checkin_id` が入った行があれば `regen_done` で止める（errcode P0001。Edge Function が 409 にする）。`p_rows` が空なら何も書かずに今の組を返す（回数を使わない）。それ以外は `p_rows` を generation 2 で挿入して返す。
   - 戻り値: 今の組の `daily_hints` の行（slot 順）。
   - 権限: `security definer`、`set search_path = ''`、実行は service_role だけ（0002 と同じ書き方で revoke / grant）。
   - ロックをすり抜けても、一意制約と generation の CHECK が2組目・3組目を DB で止める（二重の守り）。
3. **置き換え `perform_checkin`（気配の +10 を組み込む）**
   - 0003 の動き（同じ店は1日1回、2回目は `already_today`）はそのまま残す。
   - 引数を1つ足す: `p_alt_shop_id text`（気配の照合にだけ使う「同じ店の別の id」。§5.3。無ければ NULL）。
   - 戻り値に `was_hint boolean` を足し、`coins_awarded` は 30 か 40 になる。
   - 引数と戻り値の形が変わるので、`create or replace` では置き換えられない。**古い関数を `drop function public.perform_checkin(uuid, text, boolean, date, jsonb)` してから作り直し**、権限（service_role だけ）を付け直す。
   - 流れ（足す所に ★）:
     1. プロフィールの確認（今までどおり）。
     2. ★ 今日の気配を探す: `daily_hints` から `user_id = p_user`・`hint_date = p_day`・**その日の一番大きい generation**・`shop_id in (p_shop_id, p_alt_shop_id)`・`completed_checkin_id is null` の行を1つ、`FOR UPDATE` で取る。
     3. `checkins` に挿入（★ `was_hint` に「2で見つかったか」を入れる）。今日すでに済みなら `already_today`（今までどおり）。
     4. `coin_ledger` に `checkin` 30（今までどおり）。★ 気配なら `hint_bonus` 10 も入れる（DB 設計どおり2行で記録。金額は CHECK で 10 に固定済み、`(checkin_id, reason)` の一意で二重付与も止まる）。
     5. ★ 気配なら `daily_hints.completed_checkin_id` にこのチェックインを入れる。
     6. 霧のセル（今までどおり）。
     7. 返す: `checkin_id`、`coins_awarded`（30 か 40）、`new_cells`、★ `was_hint`。
   - `was_hint` はブラウザの申告ではなく、この関数が `daily_hints` を見て決める（DB 設計 3.5 の注記のとおり）。
   - 昨日の気配・作り直す前の組の気配は 2 に当たらないので +10 は付かない。

適用: 開発用 Supabase `mogumo-go-dev` の SQL Editor に貼って Run（0002・0003 と同じ）。本番には今回は流さない（§2）。

### 5.3 同じ店の id が端末とサーバーでずれる場合（`p_alt_shop_id`）
地図の店（`osm:`）とホットペッパーの店（`hp:`）は端末で合体する（`src/shops/domain/merge.ts`。合体後の id は `hp:…`、元の点は `mapId`）。ホットペッパーの読み込みのタイミングで、合体したりしなかったりするので、気配の id とチェックインの id がずれることがある。どちらの向きも「サーバーで同じ店だと確かめられたときだけ」+10 を付ける（設計役の判断。確認役が「自分で決められる」とした点）。

| 気配の店 | チェックインの id | 起きる時 | `checkin` の Edge Function の扱い |
|---|---|---|---|
| `osm:Y`（謎の気配） | `hp:X`（あとで合体した） | 候補を集めた時はホットペッパーとまだ合体していなかった | 端末は今までどおり `map_id = osm:Y` を送る。**`osm:Y` が今日の今の組の未達成の気配のときだけ**、地図タイルでその点を確かめ、`hp:X` の位置から 40m 以内（`MATCH_M`）なら `p_alt_shop_id = osm:Y` |
| `hp:X` | `osm:Y`（合体していない） | チェックインの時、ホットペッパーの読み込みに失敗していた | `osm:Y` はタイルで確かめる（今までどおり）。今日の今の組に未達成の `hp:` の気配があり、その店の位置が確かめた点から 40m 以内で、**店名が同じ店とみなせる**（`normalizeName` が互いを含む。§6.4 でサーバーに写すもの）なら `p_alt_shop_id = hp:X` |

- 関係ない `map_id` を送って +10 を取ることはできない（気配の店でないと見ない・タイルと位置と名前で確かめる）。
- 端末は、ホットペッパーの読み込みが済んでから候補を集め（§7.1）、気配の店のピン・明かしの判定は `id` と `mapId` の両方で照合する。

### 5.4 複数の端末（設計役の判断）
- 気配の組・作り直しの回数・達成は**サーバーが正本**なので、iPhone と PC で同じ気配になる。同時に作ろうとしても `create_daily_hints` のロックで1組になる。
- 「明かした」の記録だけは端末ごと（localStorage）。別の端末では、もう一度 30m に入るか、達成すれば明かされる。困ることは少ないので、サーバーには持たない。
- 作り直しは片方の端末でしたら、もう片方は次にシートを開いたときに新しい組を読む（`useDailyHints` は探索シートを開くたびに今の組を読み直す）。

## 6. Edge Function `daily-hints`（新規）

置き場所: `supabase/functions/daily-hints/`（`index.ts` が Deno の本体、`core.ts` が純粋な計算で Vitest から読む。既存2つと同じ形）。

### 6.1 入力
`POST`、JWT 必須（ユーザーは JWT からだけ決める。既存と同じ確かめ方）。本文:
```
{
  "regen": false,                                    // true なら「この辺りで探し直す」
  "hp":  ["hp:J001234567", ...],                     // ホットペッパーの情報がある候補の id（最大 HINT_MAX_HP_CANDIDATES）
  "osm": [{ "id": "osm:123", "lat": 35.6, "lng": 139.6 }, ...]  // 地図だけの候補（最大 HINT_MAX_OSM_CANDIDATES）。lat/lng は「店の」位置
}
```
- 形が違う・上限を超える・id の形が `^hp:[A-Za-z0-9]{1,32}$` / `^osm:\d+$` でない → 400。
- 自宅・現在地・距離・速さは受け取らない（項目自体が無い）。

### 6.2 出力
```
200 {
  "hint_date": "2026-11-07",
  "generation": 1,
  "regen_left": 1,                                   // 今日あと何回作り直せるか（0 か 1）
  "hints": [
    { "hint_id": "...", "slot": 1, "shop_id": "hp:...", "hint_genre": "中華", "hint_catch": "自家製麺の濃厚つけ麺",
      "hint_budget": "1,000円台", "is_mystery": false, "completed": false,
      "shop": { "name": "…", "lat": 35.6, "lng": 139.6 } },
    ...
  ]
}
```
- `hints` が空 ＝ 今日は気配なし。
- 店名（`shop.name`）も返す（N-04「店名は端末の画面で伏せるだけ（データは届く）」）。端末は 30m までは画面に出さない。
- エラー: 401 unauthorized／400 bad_request／409 profile_missing・regen_used・regen_done・no_hints・not_far（§6.3）／500 internal_error。地図タイルが読めないのは謎の気配が出せないだけなので、エラーにせずホットペッパーの店で埋める（§6.3）。
- ログ: 候補の id・位置・ユーザー id・トークンを出さない（既存と同じ方針。`console.error('daily-hints failed')` のような固定の文だけ）。

### 6.3 処理の流れと、二重生成・作り直しの守り
1. JWT を確かめる。`day = jstDay(new Date())`（サーバーの日付が正本）。
2. **作り直しでなく、今日の行がすでにあれば、今の組を返して終わり**（候補は見ない）。安い道を先に通す。
3. 作り直しのときの事前の確かめ（安い順）: 今の組が無い → `no_hints`、すでに作り直し済み → `regen_used`、達成した気配がある → `regen_done`。
4. 候補を確かめる（端末の言うことは信じない）:
   - `hp` 候補: `shops` に行があり、名前がある店だけ残す。ヒントの材料（ジャンル・キャッチ・予算）は**端末から受け取らず `shops` の行から作る**。
   - 未訪問: その人の `checkins` に、候補の `shop_id` があれば外す（`hp` も `osm` も）。
   - 作り直しのときは、残った候補の位置の重心が、今の組の店の位置の重心から `HINT_REGEN_MIN_M`（1.5km）以上離れていなければ `not_far`（同じ場所での引き直しを防ぐ。店の位置どうしを比べるだけなので、自宅も現在地も使わない）。
5. 抽選（`core.ts` の純粋な関数。乱数は引数で渡し、テストで固定できるようにする）:
   1. 謎の気配の日か: `random() < HINT_MYSTERY_DAY_RATE`（0.25 ＝ 4日に1回くらい）かつ `osm` 候補がある。**リーダーの判断**。作り直しの組でも同じ規則で引き直す。
   2. 謎の日なら `hp` から 2件、`osm` から 1件（`HINT_MYSTERY_PER_DAY`）。ふつうの日は `hp` から 3件。どれも重ならないようにランダムに選ぶ。
   3. **候補が足りない日（リーダーの判断）**:
      - `hp` が足りない → 足りない分を `osm`（謎の気配）で埋める（ふつうの日でも）。
      - 謎の日なのに `osm` が無い → `hp` で3件。
      - それでも合計が3件に届かない → あるだけ（1〜2件）で作る。
      - 合計0件 → 行を作らず `hints: []` を返す（気配なし。作り直しなら今の組をそのまま返し、回数は使わない）。
   4. 枠（slot）はランダムに並べる（謎の気配がいつも3番目にならないように）。
6. 謎の気配に選んだ `osm` の店を確かめる: 地図タイル（OpenFreeMap、`checkin` と同じ読み方）で、**店の位置**のタイルにその番号の「名前のある飲食店の点」があるか。あれば `shops` に upsert（名前・位置・`genre_name` は地図の種類。`checkin` が地図の店を書くときと同じ）。無ければ次の `osm` 候補で試す（最大 `HINT_MYSTERY_VERIFY_TRIES` 回）。だめなら `hp` 候補で埋める。タイルが読めないときも `hp` で埋める。
   - 地図タイルの読み方は今 `checkin/index.ts` の中にある。`supabase/functions/_shared/osmTile.ts` に移して2つの関数で共有する（`checkin` の動きは変えない）。
7. `create_daily_hints(user, day, regen, rows)` を1回呼ぶ（§5.2）。返ってきた行（先に別の要求が作った分のこともある）に `shops` の名前・位置を付けて返す。
- 二重生成の守りは3段: ①最初に「今日の行があるか」を見る ②SQL 関数が本人の行をロックしてから確かめる ③一意制約と generation の CHECK。
- 作り直しの回数を数えるのはサーバー（`generation` の最大値）。端末の言う回数は使わない。
- 気配なし（0件）の日は行が無いので、次に探索シートを開いたときにもう一度作ろうとする（**リーダーの判断**）。0件のうちは「1日1回」の数に入らない。

### 6.4 ヒントの作り方（`core.ts`、`hp` の店だけ）
**ジャンル（あいまい表示）**
- `hint_genre` には `shops.genre_name`（ホットペッパーのジャンル名）をそのまま入れる。画面で後ろに「？」を付けて「中華？」「居酒屋？」と出す。
- ジャンル名が無い `hp` の店は、`hint_genre = NULL` のまま `is_mystery = false`（画面では「ジャンル？」とだけ出す）。謎の気配は地図だけの店に限る（オーナー決定）。

**キャッチの断片**（S5「キャッチコピーの断片」）
1. キャッチが無ければ NULL。
2. 【 】［ ］《 》≪ ≫ などのかっこを中身ごと消す（駅からの道のりや宣伝が入りやすい）。
3. 区切り（`。！!？?♪☆★◆◇■□●○／/、,…` と空白・改行）で短い切れ端に分ける。
4. 外す切れ端: **店名を含むもの**（名前の比べ方は `src/shops/domain/merge.ts` の `normalizeName` と同じならし方。サーバー側に同じ式を写し、`keep in sync` と書く。§5.3 の名前の照合にも使う）、「駅」「徒歩」を含むもの、3文字以下のもの。
5. 残りの最初の切れ端を使う。`HINT_CATCH_MAX_CHARS`（14文字）を超えたら切って「…」を付ける。
6. 残らなければ NULL。
- 画面では「…自家製麺の濃厚つけ麺…」のように前後に「…」を付けて「断片」らしく見せる。
- 店名がカタカナと漢字で書き分けられているなど、完全には消しきれない場合がある（初版の割り切り）。

**予算の言いかえ（リーダーの判断: 短く言いかえる）**
`shops.budget_name`（例「1001～1500円」「～500円」「30001円～」）を、次の規則で短くする。
1. 数字のカンマと全角・半角の違いをならす（「～」「〜」「~」は同じ扱い）。
2. 下の端の金額 L を取る。「～500円」のように下の端が無ければ L = 0。「30001円～」は L = 30001。
3. L を言いかえる:

| L | 言いかえ | 例 |
|---|---|---|
| 1000 未満 | 「〜1,000円」 | 「～500円」「501～1000円」→「〜1,000円」 |
| 1000 以上 10000 未満 | 千の位で切り捨てて「N,000円台」 | 「1001～1500円」→「1,000円台」、「2001～3000円」→「2,000円台」、「5001～7000円」→「5,000円台」 |
| 10000 以上 | 万の位で切り捨てて「N万円台」 | 「10001～15000円」→「1万円台」、「30001円～」→「3万円台」 |

4. 数字が読めない書き方なら、元の文字をそのまま入れる。予算が無ければ NULL。
- 画面では「予算 1,000円台」と出す。

**謎の気配**
- `hint_genre`・`hint_catch`・`hint_budget` はすべて NULL、`is_mystery = true`。

## 7. 端末側

### 7.1 候補の集め方（`src/hints/domain/candidates.ts`、純粋な関数）
材料は、地図がすでに持っている情報だけ（新しい問い合わせはしない）:
- `shops`: 合体済みのお店の一覧（`worldLayers` の `shops`。今いる場所のまわり 1km の分）
- `cleared`: 晴れたセル（自宅 200m＋サーバーのセル＋今後ルート）
- `checked`: 済みの店 id（合体した店は地図の点の id でも済み。`worldLayers` の `checkedNow`）
- `home`（端末の自宅）、`me`（今の位置）

ルール:
1. **範囲**
   - 自宅から `HINT_HOME_RADIUS_M`（1km）以内にいる → 自宅から 1km 以内の店。
   - 自宅の範囲の外にいる → 自宅から 1km 以内の店 **と** 今いる場所から `HINT_AWAY_RADIUS_M`（1km）以内の店（S10「今いる場所の周りからも」）。
   - 作り直しのとき → 今いる場所から 1km 以内の店だけ（「この辺りで探し直す」なので）。
   - 自宅が無い（ふつうは起きない）→ 今いる場所のまわりだけ。
   - **割り切り（オーナー決定 2026-11-07 で受け入れ）**: 端末が読み込んでいる店は「今いる場所のまわり 1km」だけなので、気配は実際には「**作った時にいた場所のまわり**」が中心になる。自宅の範囲の中でも、今いる場所から遠い側の店は候補に入らない。自宅の外で作れば、出先のまわりの気配になる。自宅を中心に店を問い合わせると自宅の位置をサーバーに教えることになるので、**わざわざ取りに行かない**。この偏りを、§7.3 の「作る時の工夫」で小さくする。
2. **霧の中**: 店の位置のセルが晴れていない（`isClearedAt(cleared, shop)` が false）。
3. **未訪問**: `checked` に無い（`id` でも `mapId` でも）。
4. **名前がある**（S9: 名前が無い店は対象外）。
5. 振り分け: `id` が `hp:` で始まる → `hp` 候補（id だけ送る）。`osm:` で `details` が無い → `osm` 候補（id と店の位置）。
6. 上限を超えたらランダムに間引く（乱数は引数）。

### 7.2 送る情報の最小化
- 送る: `regen`（作り直しか）、`hp` の id の一覧、`osm` の id と店の位置の一覧。
- 送らない: 自宅、現在地、距離、方角、速さ、晴れたセル、自宅の範囲の内か外か。
- `daily-hints` の呼び出しは**その日の気配が無いとき（と作り直しのとき）だけ**（毎回は送らない）。

### 7.3 流れと、作る時の工夫（`src/hints/ui/useDailyHints.ts`）
**読むだけ（アプリを開いたとき）**
1. ログイン後、地図を開いたら、`daily_hints` を直接読む（RLS で本人の行だけ）。`hint_date = jstDay(今)` の一番大きい generation の組を、`shops(name, lat, lng)` と一緒に読む。あればピンを出す。**ここでは作らない**。

**作る（その日初めて探索シートを開いたとき。オーナー決定 a）**
2. 探索シートを開くたびに、今の組を読み直す（別の端末で作った・作り直した分を拾う。§5.4）。
3. 今の組が無ければ、次の順に確かめる:
   1. ホットペッパーが使えない環境（`shopSourceEnabled` が false。今の本番）→「いまは気配を探せません」（作らない）。
   2. **速く動いている（オーナー決定 b）**: 速さが `HINT_FAST_KMH`（時速15km）を超えている → 「降りたら今日の気配が出るよ」と出して作らない。シートを開いたまま歩く速さ以下になったら、その場で作る。シートを閉じていたら、次に開いたときに作る。
      - 速さの取り方・ならし方（GPS の `coords.speed` を使うか、位置の差から出すか、何秒分をならすか）と、速さが取れないときの扱い（例: 取れない間は「遅い」とみなす）は**作る人に任せる**。目安として、駅で止まっただけで作らないよう、数十秒ほど遅い状態が続いてから作るのがよい。今の `judgeFix`（`src/map/domain/smoothing.ts`）は秒速30m を超える飛びを捨てるので、新幹線などではそもそも位置が更新されにくい点に注意。
   3. お店の読み込みがそろうのを待つ: 「ホットペッパーの読み込みが1回成功」「地図のお店の取り出しが済んだ」「保存済みの進み具合（`loadProgress`）の読み込みが済んだ」の3つ。`worldLayers` に「そろった」を知らせる口を足す（§9）。待つ間は「気配を探しています…」（D-17）。`HINT_READY_TIMEOUT_MS`（30秒）待ってもそろわなければ「いまは気配を探せません。少し歩いてから開き直してね」（仮の文）。
   4. 候補を集め（§7.1）、`daily-hints` を呼ぶ。返ってきた `hint_date`・`generation`・`regen_left`・行を使う（端末の時計がずれていてもサーバーの日付に従う）。
4. 地図は待たせない（気配の処理は全部裏で動く）。
5. 失敗（通信など）→ 「気配を読み込めませんでした」＋「もう一度」ボタン。自動のやり直しは1回だけ。
6. 0件（気配なし）なら §8.6 を出す。次に探索シートを開いたとき、もう一度作ろうとする（**リーダーの判断**）。

**この辺りで探し直す（オーナー決定 c）**
7. 次の3つを全部満たすとき、探索シートに「この辺りで探し直す」ボタンを出す:
   - 今の組の店の位置の重心から、今いる場所が `HINT_REGEN_MIN_M`（1.5km）以上離れている（端末で計算。送らない）
   - 今の組に達成した気配が無い
   - サーバーが返した `regen_left` が 1
8. 押すと、今いる場所のまわり 1km の候補（§7.1 の作り直しの範囲）を集め、`regen: true` で呼ぶ。速い間は押せない（「降りてから探し直してね」）。
9. 409 が返ったら（`regen_used`・`regen_done`・`not_far`）、ボタンを消して今の組を読み直す。0件だったら「この辺りには気配がありませんでした」（仮の文）と出し、今の組のまま（回数は使っていない）。
10. 作り直したら、古い組のピンを消し、新しい組のピンを出す。古い組の「明かした」記録は捨てる。

**日付の切り替わり**
11. 画面が前に戻ったとき（`visibilitychange`）と、`HINT_DAY_CHECK_MS`（1分）ごとに `jstDay` を見て、変わっていたら気配を消す。次に探索シートを開いたとき新しい組を作る。

**チェックインのあと**
12. チェックインの結果 `was_hint = true` が返ったら、その気配を「達成」にする（読み直さずに手元で更新）。達成があると「この辺りで探し直す」は出なくなる。

### 7.4 店名を明かす（30m）
- `src/hints/domain/reveal.ts`: 今の位置（ならした位置。`MapView` が `onPosition` で渡すもの）と気配の店の距離が `HINT_REVEAL_M`（30m）以内なら「明かす」。
- 一度明かしたら、その日は明かしたまま（GPS のぶれで伏せ直さない）。明かした気配の id は localStorage `mogumo.hintsRevealed.<userId>` に `{ day, ids }` で持つ（自宅とは関係ない情報なので端末に置いてよい）。日付が変われば・作り直したら捨てる。
- 気配の店にチェックインしたら（`completed`）、30m に入っていなくても明かした扱いにする。
- 店の位置は、端末の合体済みの店（`id` か `mapId` が気配の `shop_id` と同じもの）があればその位置（地図の点）、無ければ `shops` の位置。ピンの位置・距離の表示も同じ。

### 7.5 他の画面で店名を伏せる（リーダーの判断を含む）
霧の中でも 50m 以内の店は建物が見え（`IN_FOG_VISIBLE_M`）、押すとお店のシートが開く。30m より外でも店名が出てしまうので:
- お店のシート（`ShopSheet`）とビルの一覧（`BuildingSheet`）は、**今日の今の組の、まだ明かしていない気配の店**なら、店名を「？？？」にする。営業時間など、ホットペッパーの詳細もヒントと同じ出し方にそろえる。
- 写真: 今のお店のシートに写真は出ていない（`ShopSheet` は名前・営業時間・距離だけ）。のちに写真を足すときは、まだ明かしていない気配の店では**写真も伏せる**（看板や外観で店名が分かるため。設計役の判断）。
- チェックインは 50m のまま押せる（S5「チェックイン可能距離（50m）とは別ルール」）。**30〜50m でチェックインした場合は、店名を伏せたままチェックインし、チェックインの演出の中で正体（店名）を出す**（リーダーの判断）。

### 7.6 地図にもともとある店名の文字（リーダーの判断）
- OpenFreeMap の地図には、お店の点（`poi` の層）の名前の文字がもともと出る場合がある。`src/map/infra/theme.ts` は今、symbol の層のうち道路番号の看板（shield）・地名・道路名しか消していないので、**霧の中の気配の店名が地図の文字で見えてしまうおそれがある**。
- 実装の最初（§13 の手順1）に、dev の地図で霧の中のお店の名前の文字が見えるか確かめる。見えるなら `theme.ts` で `poi` の層の文字を消す（お店は 3D の建物とピンで出しているので、地図の文字は要らない）。
- 注意: 地図のお店の取り出し（`src/shops/infra/mapShops.ts`）は `querySourceFeatures` で `poi` を読んでいる。層を隠してもタイルのデータは読めるはずだが、消したあとにお店が出続けることを必ず確かめる。だめなら層を消さずに文字の不透明度を 0 にする。

- 地図の中のもの（ピンの位置・カメラ）は今までどおり `MapView` の中で持ち、`MapViewHandle` に口を足す（§9）。

## 10. テストの方針

- **domain（中心）**
  - `candidates`: 自宅の範囲の内／外、作り直しは今いる場所のまわりだけ、霧の中だけ、晴れた店は外れる、済み（id・mapId）は外れる、名前なしは外れる、`hp`・`osm` の振り分け、上限で間引く（乱数を固定）。
  - `hint`: 「中華？」、ジャンル無し、謎の気配の文、断片に「…」、距離の丸め（84m→約80m、99m→約100m、120m→約100m、430m→約450m など境目。四捨五入）。
  - `reveal`: 30m ちょうど・31m、一度明かしたら離れても明かしたまま、達成で明かす、作り直しで捨てる。
  - `when`: 時速15km ちょうど・超え、「探し直す」の3条件（1.5km ちょうど・未満、達成あり、regen_left 0）。
- **サーバーの core（Vitest で `core.ts` だけ読む。既存と同じ）**
  - 入力の確かめ（形・上限・id の形・regen）。
  - 抽選: ふつうの日は hp 3件、謎の日は hp 2＋osm 1、hp 不足を osm で埋める、謎の日に osm 無し、合計1〜2件、0件、重複なし、slot が 1 から詰まる（乱数を固定）。
  - 作り直しの重心の判定（1.5km 以上・未満）。
  - キャッチの断片: かっこを消す、店名入りを外す、駅・徒歩を外す、14文字で切る、残らないと NULL。
  - 予算の言いかえ: 「～500円」「501～1000円」「1001～1500円」「5001～7000円」「10001～15000円」「30001円～」、全角・カンマ、読めない書き方はそのまま。
  - 店名の照合（§5.3 の hp 気配に osm でチェックイン）。
  - `osmTile` を `_shared` に移したあとも `checkin` の既存テストが通ること。
- **infra**: `hintsApi` の返事の読み取り（壊れた形は捨てる、409 の種類、40 と `was_hint`）、時間切れ、`revealStore` の日付の切り替え。`hintPins` は作る・入れ替える・消すの最小限（MapLibre はモック。ビルのピンのテストにならう）。
- **ui（Testing Library）**: 探索シートの状態（読み込み中・速い・探せない・3件・達成あり・探し直すボタンあり／なし・気配なし・失敗）、シートを開いたときだけ作る（開くまで `daily-hints` を呼ばない）、ヒントのシートに店名が出ないこと、お店のシート・ビルの一覧で伏せること、明かしの帯、伏せたままチェックインしたときの演出の正体。
- **DB（手で確かめる。開発用 Supabase）**: 同じ日に2回作っても1組、同時に2回呼んでも1組、作り直しで generation 2 ができ古い組が残る、2回目の作り直しは `regen_used`、達成後の作り直しは `regen_done`、気配の店へのチェックインで 30＋10 の2行・`was_hint = true`・`completed_checkin_id` が入る、気配でない店・昨日の気配・作り直す前の組の店は 30 だけ、他人の `daily_hints` は読めない、authenticated から関数を実行できない。
- 全体: `npm test`・`npx tsc -b`・`npm run lint`・`npm run build`。

## 15. 決定（2026-11-07。オーナーの回答とリーダーの判断）

### オーナー決定
1. **自宅の外で作られる日があることは受け入れる**。S10 は、端末の読み込み範囲の都合で「作った時にいた場所のまわり」中心になる（§7.1 に明記）。そのかわり作る時を次の3つで工夫する（全部採用）:
   - a. 生成はアプリを開いたときではなく、**その日初めて「探索」ボタンを押してシートを開いたとき**（§7.3）。
   - b. **速く動いている間（GPS の速さが時速15km 超。電車・車）は作らず**、シートに「降りたら今日の気配が出るよ」と出す。止まる・歩く速さになったら作る。速さのならし方・GPS の速さが取れない時の扱いは作る人に任せる（§7.3）。
   - c. **今日の気配の場所（3件の重心）から 1.5km 以上離れていて、まだ1件も達成していなければ「この辺りで探し直す」**。押すと今いる場所のまわりで3件を作り直す。1日1回だけで、回数はサーバーが数える（`daily_hints.generation`。古い組は消さずに残す。§5・§6.3）。
2. **本番（main）にはまだ出さない**。今回は開発用 `mogumo-go-dev` だけで動けばよい。本番の準備は範囲外（§2「しないこと」）。

### リーダーの判断
3. ホットペッパーの店が足りない日は謎の気配で埋め、それでも足りなければ1〜2件の日もある（§6.3）。
4. 謎の気配は 4日に1回くらい・3件中1件（調整値 `HINT_MYSTERY_DAY_RATE`・`HINT_MYSTERY_PER_DAY`）。
5. 気配なしの日は、探索シートに近い未訪問店3件。押すとカメラ移動。絵は無し（文字だけ）（§8.6）。
6. 30〜50m でチェックインしたら、店名を伏せたままチェックインし、演出で正体が分かる（§7.5・§8.5）。
7. 予算は短く言いかえる（例「1001～1500円」→「1,000円台」。規則は §6.4）。
8. 気配0件の日は、探索シートを開くたびに作り直しを試みる（§6.3・§7.3）。
9. 方角は出さない。距離はシートに「ここから 約400m」（端末で計算。§8.2）。
10. 地図にもともとある店名の文字（OpenFreeMap の `poi` の層）で店名がばれないか実装の最初に確かめ、見えるなら `poi` の層の文字を消す（§7.6）。

### 設計役の判断（確認役が「自分で決められる」とした点）
11. `hp:` の気配に `osm:` でチェックインしたとき（と、その逆）は、サーバーが位置（40m 以内）と店名（逆向きは位置だけでなく名前も）で同じ店と確かめられたときだけ +10（§5.3）。
12. 複数の端末: 気配・作り直しの回数・達成はサーバーが正本で同じになる。「明かした」だけは端末ごと（§5.4）。
