## 2. 決定済みの仕様

### 2.1 形・着手（2026-11-04 本人決定）
- Web アプリ（スマホのブラウザで遊ぶ）
- 採用案は **A・B・E の混合**。今夜（2026-11-04）から着手する

### 2.2 共通の土台（資料 §5。全案共通＝採用案の土台でもある）
- 地図が霧で覆われている
- 歩いた所と、行ったお店の周りが晴れる
- 毎日クエストが出る
- 違うのは「何を一番の楽しさにするか（芯）」だけ → 採用した芯は A・B・E の3つ
- **霧の晴れ方: 不定形（雲が晴れるような有機的な形、境界はグラデーションでぼんやり）**（2026-11-04 本人決定。円・マス目・街区・道沿いの帯のイメージと比較して選択）
  - 技術含み（未決定・技術選定で確認）: 見た目が不定形だと「晴れた割合」を直接は数えられないため、内部の管理・開拓率の計算は細かいマスで持ち、表示だけ不定形にする分離が現実的

### 2.3 案A の芯: 霧を晴らすクエスト（クエストの報酬が霧を晴らす）
- 種: 「会社の周りのお店を開拓するのが楽しくなるアプリがほしい。毎日ちょっとした目標があるといい」
  - ※種の文面は資料のまま。「会社の周り」の部分は §2.5 の範囲決定（自宅設定＋現在地）で読み替える
- イメージ: 歩くだけでも霧は少し晴れるが、クエストを達成すると大きく晴れる
  - 例: 「まだ行っていない喫茶店に行く → その店の周り 200m が晴れる」
- スクショの姿: 霧の中に、クエストで晴れた丸がいくつも浮かぶ地図
- 発掘の種（→ 論点 S2・S3・S4）: 晴れる大きさ／「行った」の判定（店の前を通っただけで達成か）／クエストが出せない日（近くに条件の店が無い）

### 2.4 案B の芯: 霧の向こうのお題（クエストの行き先が霧の中に隠れている）
- 種: 「新しいお店に行くきっかけがほしい。行くまで何の店か分からないとわくわくする」
- イメージ: クエストはヒントだけ。例: 「霧の中、北東 400m に未訪問のお店がある。ジャンルはカレー」。近づくと霧が晴れて店名が出る
- スクショの姿: 霧の中にヒントの印がある地図と、晴れて正体が分かった後の地図の2枚
- 発掘の種（→ 論点 S5）: ヒントをどこまで出すか／近づいたの判定の距離（位置の誤差は数十m ある）／ジャンルが分からない店をお題にするか

### 2.5 範囲と拠点（2026-11-04 本人決定。資料 §3・§6-4 への回答）
- 全国はやらない（資料の前提どおり）
- **お店の表示: 常に「その人がいる場所」の周りのお店が出てくる**（現在地連動）
- **探索の拠点: 「自宅」を設定して、そこからの探索**にする
- **自宅は特定の住所に固定しない。誰でも自分の自宅を設定して使える汎用仕様**にする（「家からの探索だけど、誰の家でもできる」）
- 資料の論点との対応: 案D の発掘の種にあった「自宅の位置という個人情報をどこに置くか」→ 自宅の座標は利用者の端末の中だけに置く方向が自然（§4 の「自分の記録はブラウザの中だけ」と同型）。最終確定は技術選定フェーズ
- **探索半径: 自宅（拠点）から半径 1km**（2026-11-04 本人決定。技術選定フェーズで Overpass の実件数を見て見直す余地あり）
- 未決定: 現在地の周りのお店の表示範囲（地図の表示にどう追随させるか。→ 論点 S1 の残件）

### 2.6 案E の芯: 5週間の開拓記（変化の記録。発表のスクショから逆算する）
- 種: 「どれだけ開拓したかを、あとで振り返れるようにしたい」
- イメージ: 霧晴らしとクエストに加えて、日ごとの開拓の記録を残す。「1週目 → 5週目」の霧の地図を並べて見られる
- スクショの姿: 始めた日と最後の日の地図を並べた画面（発表の「成長」の話にそのまま重なる）
- 発掘の種（→ 論点 S6）: 何を記録するか（晴れたマス・行った店・達成したクエスト）／記録が消えたとき／いつから記録を始めるか（作っている途中のデータをどうするか）
- **注意（資料明記）: 記録を見せるには、作り始めの早い段階で記録の機能を入れておく必要がある。後から作ると5週分のデータが無い** → PDCA の早い周に記録を入れる

## 3. 地図とお店のデータ（資料 §3。選定は技術選定フェーズ）

- **今回は完全無料でやる**【決定 2026-11-04】: 初版は課金ゼロ。Google Maps Platform は無料枠内でも請求アカウント（カード登録）が必須のため使わず、無料構成（MapLibre／Protomaps／OSM系／OSRM等）を第一候補にする

### 3.1 資料の回答（懸念へのこたえ）
- 全国は要らない。このアプリで要るのは「自分が歩ける範囲のお店」だけ
- 範囲の例: 「会社の周り 1km」「自宅の周り 1km」。これを決めるのが要件定義の最初の仕事
- お店の情報は OpenStreetMap の Overpass API で、範囲（四角か円）を指定して1回問い合わせれば取れる見込み（amenity=restaurant・cafe・fast_food など）。1km 四方なら数十〜数百件の規模
- 取った結果は JSON にしてアプリに同梱すれば、遊ぶたびに API を呼ばなくてよい。データの更新はたまに手で
- 地図の絵（タイル）は Leaflet ＋ OpenStreetMap のタイル。出典の表示と、アクセスの頻度の決まりを守ることも要件に入れる
- **注意: データは汚い。** 店の名前が無い・ジャンル（cuisine）が無い・閉店した店が残っている、などが普通にある。どう扱うかも要件（→ 論点 S9）

- **フロントは React＋TypeScript＋Vite、ホスティングは Vercel（無料）**【決定 2026-11-04】: 地図が主役のSPA。MapLibreの事例とAI生成の安定度で React が最適、Next.js は今回過剰。滑らかさの要件：ピンは地図レイヤーで描く／地図移動で React を再描画しない／GPS更新間を補間してアバターを歩かせる。最初の1周の受け入れ条件に「実機でヌルヌル動くこと」を入れる
- **サーバーは Supabase（無料枠）**【決定 2026-11-04】: Googleログイン／PostgreSQL／写真ストレージ／APIキー中継の Edge Functions を1か所で。カード不要。制約として記録：無料プロジェクトは約1週間の低活動で一時停止（警告メールあり・1年以内は復旧可）、写真は転送量（月5GB）に合わせて150〜250KBへ圧縮、リージョンは作成時に東京を選ぶ。次点は Neon。調査の正本は ~/workspace/research_notes/baas-choice-personal-dev-gourmet-app-20261104-1245/report.md。**再確認事項（未決定）**: 2026-11-04 夜に本人から「上司の課題はバックエンド開発だったのでは」との疑問が出ており、Supabase のまま進めるか自作 API サーバー寄りにするかの再確認が残っている。Supabase プロジェクトの作成前に本人が確定する
- **地図は MapLibre GL JS ＋ OpenFreeMap**【決定 2026-11-04】: 完全無料・登録/APIキー/カード不要、傾け（45〜60°）対応、スタイルは自前JSONでカスタム。出典表示（OpenFreeMap／OpenMapTiles／OpenStreetMap）は必須。無保証・予告なく止まる可能性に備え、タイルの出どころは設定1か所で差し替え可能に設計する（逃げ先＝Protomaps自前配布）。ルート描画は OSRM（FOSSGIS版、キー不要・1回/秒までの節度利用）をセットで採用。調査の正本は ~/workspace/research_notes/free-map-integration-gourmet-app-20261104-1230/report.md
- **お店データはホットペッパーグルメAPI**【決定 2026-11-04】: 無料・写真あり・ジャンルあり。掲載店のみ／評価なし／商用不可（学習・個人利用の範囲）。2026-11-02 の調査で候補化していたもの

### 3.2 地図はどこまで正確である必要があるか（資料 §3。未選定＝技術選定で決める）
- Google マップほど正確である必要があるかは決まっていない。**正確さと費用・手間の釣り合いを決めるのも要件定義**。選んだ理由を要件定義書に書く
- 地図には「背景の絵（道や建物）」と「お店のデータ」の2つがあり、別々に選べる

| 候補 | 背景の絵 | お店のデータ | 費用・手間 | 気をつけること |
|---|---|---|---|---|
| OpenStreetMap（Leaflet＋OSM のタイル、Overpass API） | ○ | △ 地域で差が大きい（名前・ジャンルの欠け、閉店した店が残る） | 無料・API キー不要 | 出典の表示とアクセスの頻度の決まりを守る |
| 無料のベクターデータを自分で配る（OSM 由来のデータを1つのファイルにして、GitHub Pages などに置く。例: Protomaps） | ○ 色や見せ方を自由に変えられる（霧の表現と相性がよい） | お店は別に用意する | 無料。範囲を切り出して置く手間がある | 範囲を絞れば軽い |
| 国土地理院の地図（地理院タイル・ベクトルタイル） | ◎ 道・建物は正確 | ✕ お店のデータは無い | 無料・API キー不要 | 出典の表示が要る。お店は OSM などと組み合わせる |
| Google マップ（Maps JavaScript API・Places API） | ◎ | ◎ 店名・ジャンル・営業時間がそろう | 無料枠はあるが、API キーと課金の登録（カード）が要る | 取ったデータの保存・加工に規約の制限がある。使いすぎると課金される |

- 資料のおすすめ: 「会社の周り 1km のお店が、だいたい合っていればよい」なら OSM で足りるかもしれない。**まず自分の範囲で Overpass API を1回呼び、何件出るか・どれくらい欠けているかを見てから決める**（その結果も苦労日誌の材料）
- お店が足りなければ、「自分で店を足せる」機能を付けるのも1つの答え（→ 論点 S9）
- （資料外・過去の調査 2026-11-02）Google Places の無料枠は SKU ごとに月単位で分かれ、取るフィールドで料金が変わる。課金前に止める本命は日次クォータ。詳細は技術選定フェーズで再確認する

### 3.3 検証場所の事情（資料 §3）

- 会社の周りを範囲にすると、外を歩いて確かめられるのが平日の昼休みだけになる
- → §2.5 の決定（自宅を設定して探索の拠点にする）は、この事情にも合っている

## 4. Web でやるときに先に知っておくこと（資料 §4。発掘の種＝要件候補）

| こと | 中身 | 手の候補 |
|---|---|---|
| スマホで位置を取るには HTTPS が要る | ブラウザの位置情報は HTTPS か localhost でしか動かない。PC で立てたローカルサーバーにスマホから http でつなぐと、位置が取れない | ① 静的なページにして GitHub Pages などで公開する（HTTPS になる）② 開発中は PC のブラウザの「位置を偽装する機能」（Chrome の開発者ツールの Sensors）で試す |
| 画面を消すと記録が止まる見込み | ブラウザは、画面を消したりほかのアプリに切り替えたりすると位置を取れなくなるのが普通。歩いた道を全部は記録できない | 「アプリを開いている間だけ記録する」と割り切る／画面を消さない仕組み（Wake Lock）を使う／お店に着いたときだけ記録する（→ 論点 S7） |
| 記録をどこに置くか | サーバーを作らないなら、ブラウザの中（localStorage など）。機種変更やキャッシュの削除で消える | 消えてよいことにする／書き出し・読み込みのボタンを付ける（→ 論点 S8） |
| iPhone と Android で振る舞いが違う | 位置の許可の出し方や精度がブラウザごとに違う | 使うスマホを1つに決めて、受け入れ基準をそのスマホで書く |

- 検証スマホ: iPhone 16（本人の使用機種。資料 §6-2 への回答。ブラウザは要確認）

### 4.1 API キーの扱い（資料 §4。Google マップなどキーが要るものを選ぶ場合）
AI と一緒に作ると、次のことが起きやすい。どう守ったか・どこで AI が危ないことをしかけたかは、基本設計書（非機能要件）と苦労日誌に残す（発表で「AI に任せてはいけない所」の具体例になる）
- AI がキーをソースに直接書き、そのままコミット・MR にする。一度 GitHub に上がると、消しても履歴に残る。公開リポジトリなら数分で拾われることもある
- AI はキーの入ったファイル（.env など）も読める。読んだ内容は会話に残る。「読ませない」なら、読ませない仕組み（置き場所・Sandbox の設定）が要る
- ブラウザで動くページに入れたキーは、誰でも見られる。静的なページでは隠せない。隠せない前提で、使える場所（自分のサイトの URL だけ）や使える API を絞る制限をキーにかける
- AI のレビュー役も見落とすことがある。「キーが入っていないか」を機械で検査する仕組み（コミット前の検査など）を自分で用意するのが確実

### 4.2 サーバーを作らない形について（資料 §4）
- サーバーを作らない形（静的なページ＋ブラウザの中の記録）なら、HTTPS の問題も「公開すれば済む」に寄せられる
- ただし公開先にほかの人が来ても困らない作りにすること（自分の記録はブラウザの中だけにある、など）
- サーバーを作るかどうか自体は未決定（資料 §6-6。技術選定フェーズで Claude と相談して決める）

## 5. 仕様の論点リスト（未決定。1つずつ決める）

資料の「発掘の種」と §3・§4 から起こした論点。技術選定に属するものは仕様の後に回す。
