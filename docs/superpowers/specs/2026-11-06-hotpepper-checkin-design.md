# 設計: ホットペッパー連携とチェックイン（Cycle 1 手順4の続き）

日付: 2026-11-06。本人とのやり取りで決めた内容。前の段は `2026-11-06-fog-and-shops-design.md`（霧は §12、Overpass の中継は §11）。

## 1. ねらい
- お店を本物にする。仮の Overpass をやめる。**お店の土台は地図のデータ（OpenStreetMap）、ホットペッパーは上乗せ**（2026-11-06 本人決定）。地図のデータで、ホットペッパーに載っていない個人店まで出す。ホットペッパーに載っている店には、ジャンル・キャッチ・予算などの詳しい情報を足す。Overpass の混雑で 502 が出る問題も、これで無くなる。
- このゲームで一番うれしい瞬間であるチェックインを作る。押すと、図鑑カードが1枚増え、お店のまわり 200m の霧が晴れ、グルメコインが 30 増える（SPEC S2・S3・§8）。
- 演出は「しっかりしたもの」にする（本人）。最終的な目標は、明るくて可愛い見た目。今回は形の決まった仮の絵で作り、絵はシロに頼む。

## 2. やること・やらないこと
**やる**
- 地図のタイル（OpenFreeMap、すでに読み込んでいるもの）から、飲食店の点（名前・場所・大まかな種類）を取り出す。
- Edge Function「お店」`shops-hotpepper`。ホットペッパーに問い合わせ、お店の控え `shops` に保存して返す。
- 地図のデータの店とホットペッパーの店を「同じ店」として突き合わせ、1つの一覧にする。
- Edge Function「チェックイン」`checkin`。距離を確かめ、チェックインの記録・晴れたセル・コインを書く。
- アプリ側の作業：
  - 自分の晴れたセル（`fog_cells`）を読み、自宅 200m と合わせて霧を描く。
  - 霧の中のお店に近づくと見えるようにする。
  - お店の板を作る。
  - チェックインの演出を作る。
- 地図の隅に、ホットペッパーの表示（クレジット）を出す。
- Overpass の部品を外す（アプリ側のコードと `supabase/functions/shops-overpass/`）。

**やらない（次の段以降）**
- 道沿いのルートで晴れる仕組み（OSRM）
- 町の制覇
- 気配・デイリー
- 週ミッション
- 図鑑の画面
- 感想と星
- コイン残高の画面
- ガチャ

**してはいけないこと（アンチゴール）**
- キーがブラウザやログに出ること
- 現在地や自宅をサーバーに保存すること
- 距離をごまかしたチェックインや、コインの二重取りができること
- チェックインしたのに霧が晴れない・コインが付かないなど、記録が途中で欠けること

## 3. 決まっていること
### 本人が決めたこと（このやり取り）
- **チェックインの始め方**: お店の建物をタップすると、下から板が出る。板の「チェックイン」ボタンは、50m 以内のときだけ押せる（近づくとボタンが出る形は作らない）。
- **霧の中のお店**: 霧の中でも、お店から 50m 以内まで近づくと見える。見本は本人の動画 `art/reference/fog-50m-visible.mp4`（本人の Downloads から取り込む）。見え方は次のとおり。
  - お店のまわりの雲だけが、ふわっと薄くなる。
  - 近づくほど薄くなる。
  - 薄くなった雲の向こうにお店の建物とピンが見える。
  - タップすると、カメラが少し寄る。
- **お店の板**（見本の動画のとおり）:
  - 中身はジャンルの絵・店名・営業時間・青い「チェックイン」ボタン。
  - 見本にある「営業中」と星は、今回は出さない。営業中かどうかはホットペッパーの営業時間の文からは正しく出せず、星は感想の機能がまだ無いため。代わりに営業時間の文をそのまま出す。
  - ボタンが押せないときは、「あと 18m」のように残りの距離を出す。
- **押したあとの演出（A 案）**: 次の順に出す。全体で約3秒。タップで飛ばせる。
  1. 紙ふぶきが舞う。
  2. 緑の「チェックイン完了」の帯（+30 コイン）が出て、お店のピンにチェックの印が付く。
  3. 霧が波のように晴れる。試作は `.superpowers/preview/spike/`。お店に近い雲の塊から順に少しふくらみ、はじけて縮んで消える。穴は外へ広がる（約1秒）。
  - スタンプとカードの演出は出さない（本人が取りやめ）。
  - 図鑑カードは見えないところで1枚増える。
- **見た目**: 今回の動きの流れは試作で OK。ただし「もっとクオリティの高い可愛い感じ」にしたい。紙ふぶき・完了の帯の飾り・コイン・チェックの印の絵はシロに頼み、届いたら差し替える（§9）。

### 前から決まっていること
- **距離**: チェックインできるのは、お店から 50m 以内（S3）。
- **コイン**: 30（S4・§8）。同じ店は1日1回まで（D-15）。チェックインそのものは何度でもできる。
- **晴れる範囲**: お店のまわり 200m（S2 ①）。サーバーの `fog_cells` に `source='shop_radius'` で保存する（D-06）。
- **お店の表示範囲**: 現在地から 1km（S1）。サーバーに送る現在地は 250m に丸める。自宅は送らない（§2.5・前の段 §11）。
- **お店の13種**（N-27）:
  - ホットペッパーのジャンルコードと店名で決める（SPEC §9 の表）。
  - パン屋は「地図のデータのパン屋」だが、ホットペッパーにはほとんど載っていない（§7 で扱う）。
- **書くのはサーバーだけ**:
  - チェックイン・晴れたセル・コインは Edge Functions だけが書く（DB 設計 3.5・3.9・3.15、RLS で本人の読み取りのみ）。
  - チェックインの記録に現在地は保存しない（D-07）。
- **ホットペッパーの決まり**（2026-11-06 に規約と表示ガイドラインを確認、N-10 の一部）:
  - 画面に「Powered by ホットペッパーグルメ Webサービス」を出し、http://webservice.recruit.co.jp/ に向けたリンクにする。文字の形でもよい。クレジットを改変しない。
  - お店の写真を出すときは「【画像提供：ホットペッパー グルメ】」も出す。
  - 保存したデータは 24 時間以内に取り直す（キャッシュの更新は 24 時間以内）。
  - 収入を得ない（学習・個人利用の範囲。SPEC の前提どおり）。
  - 呼び出し回数の上限は書かれていない。

## 4. 作り方
### 4.0 お店の出どころ（2つを合わせる。2026-11-06 本人決定）
- **土台＝地図のデータ**: 地図のタイル（OpenFreeMap、OpenMapTiles 形式）の `poi` 層。
  - 種類が `restaurant`・`cafe`・`fast_food`・`bar`・`pub`・`bakery`・`confectionery`・`ice_cream` で、名前のある点を使う。
  - Overpass は使わない。タイルはすでに地図のために読み込んでいる。
  - 2026-11-06 に試しの自宅（新宿駅の近く）で数えたら、読み込み範囲に名前つきの飲食店が約 2,400 あった。
  - 点には、タイルの中で固定の番号（feature id）がある。これを `osm:<番号>` としてお店 ID に使う。
- **上乗せ＝ホットペッパー**: 載っている店だけ、ジャンルコード・キャッチ・予算・営業時間・写真を足す。お店 ID は `hp:<ホットペッパーの ID>`。
- **突き合わせ**（domain、純粋な計算）:
  - 地図の店とホットペッパーの店が、40m 以内にあって名前が合えば同じ店とする。
  - 名前の比べ方: 空白・記号・「店」・支店名の括弧を取り、カタカナとひらがなをそろえてから、どちらかがもう一方を含めば一致。
  - 同じ店なら、ホットペッパーの情報を使い、場所は地図の点を使う（建物に合わせる計算と合うため）。お店 ID は `hp:` を使う。
  - ホットペッパーだけにある店も出す（地図に無い・名前が違う店）。
  - 一致の基準（40m・名前の比べ方）は作る人が実データで調整する。
- **地図のデータだけの店**: キャッチと予算が無い。気配の個性ヒント（次の段）は、その店では出せない。ジャンルからの決まった文で埋める（次の段で決める）。
- **種類**: 地図の `bakery` はパン屋、`confectionery`・`ice_cream` はスイーツ、`cafe` はカフェ、`bar`・`pub` は居酒屋。それ以外は店名で判定し、ホットペッパーと一致した店はジャンルコードを優先する（§4.5）。

### 4.1 選んだ作り方（本人が承認）と、選ばなかったもの
```
iPhone ── 地図のタイルから飲食店の点を取り出す（通信は増えない）
iPhone ──(250mに丸めた現在地)──▶ Edge Function shops-hotpepper ──▶ ホットペッパー
                                   └ shops に保存して返す
iPhone ──(お店ID＋今の現在地)──▶ Edge Function checkin
                                   ├ 50m 以内か確かめる（現在地は保存しない）
                                   ├ checkins（図鑑カード）・fog_cells（200m）・coin_ledger（30、1日1回）
                                   └ 結果を返す（新しく晴れたセル・コインが付いたか）
iPhone ◀── fog_cells を読む（RLS で自分の分だけ）→ 自宅 200m と合わせて霧を描く
```
- **選ばなかった作り方1**: アプリから直接ホットペッパーに問い合わせる。キーがブラウザに出るので使えない。
- **選ばなかった作り方2**: チェックインをアプリが自分で書く。距離のごまかしやコインの二重取りを止められない。DB 設計でも、書くのはサーバーだけと決めてある。
- **選ばなかった作り方3**: 地図のデータを Overpass で取る。混雑で止まる（2026-11-06 に何時間も 502）。タイルに同じデータがあるので要らない。
- **選ばなかった作り方4**: 地図のデータを地域ごと一度ダウンロードして Supabase に入れる。タイルで足りるので、取り込みの手間と更新の手間をかけない。

### 4.2 Edge Function `shops-hotpepper`
- **受け取るもの**: POST `{lat, lng}`。250m に丸めた現在地で、丸めはアプリ側と関数側の両方で行う（前の段 §11 と同じ）。JWT の確認は有効のまま。キーは Secrets の `HOTPEPPER_API_KEY`（開発用 Supabase に本人が登録済み）。
- **問い合わせ**: グルメサーチ API に `lat, lng, range=3（1000m）, count=100, format=json` で問い合わせる。位置で探すと距離順に返ると書かれているが、資料の書き方が揺れているので、作る人が実際に確かめる。100 軒より多い地域では近い 100 軒になる。足りなければ `start` で次のページを取る（最大 3 ページまで。作る人の判断）。
- **保存**:
  - 名前の無い店は捨てる（S9）。
  - 残りは `shops` に upsert する。中身は `shop_id`, `name`, `lat`, `lng`, `genre_code`, `genre_name`, `catch`, `budget_code`, `budget_name`, `photo_url`, `fetched_at`。
  - 板に出す営業時間 `open` は、DB 設計の `shops` に列が無いので、列を足す（§6 のマイグレーション）。
  - 誰の検索で入ったか・検索の中心は残さない（DB 設計 2.5）。
- **返すもの**: お店の一覧。中身は id, 名前, lat, lng, genre_code, genre_name, catch, budget_name, open, photo_url。13種の振り分けはアプリ側の domain で行う（テストしやすく、置き方の計算と同じ側にあるため）。
- **24時間の決まり**: 問い合わせのたびに取り直して上書きする。だから、表示するお店は毎回新しい。`shops` に残った古い行は、チェックインの記録が指している（RESTRICT）ので消さない。24時間を過ぎた行の扱いは §7。
- **ログ**: キー・中心の座標・キー付きの URL を出さない。
- **失敗**: ホットペッパーが 429 なら 429、それ以外の失敗は 502 を返す。アプリのやり直し（1回）と、60秒待ってからの再挑戦は今のまま。

### 4.3 Edge Function `checkin`
- **受け取るもの**: POST `{shop_id, lat, lng, far_from_home, map_id?}`。`shop_id` は `hp:…` か `osm:…`。
  - `lat, lng` は今の現在地。丸めない（50m の判定に使うため）。保存もログ出力もしない。
  - `far_from_home` は、自宅から 500m 以上先かどうかを端末が判断した真偽だけ（D-16）。
- **やること**: 1つのトランザクションで全部書く。全部書けるか、何も書かないかのどちらかにする（アンチゴールの「途中で欠ける」を防ぐ）。DB に関数（`security definer`、service_role だけが実行できる）を作り、Edge Function から呼ぶ形にする。
  1. 店を確かめる。
     - `hp:` の店は `shops` から読む。無ければ 404。
     - `osm:` の店は、アプリが送った ID と現在地から、サーバーが同じ地図のタイル（z14、現在地を含む1枚）を OpenFreeMap から取り、その番号の点があるかを確かめる。点があれば、その点の名前・場所で `shops` に upsert する（`shop_id='osm:<番号>'`、ジャンルは地図の種類）。点が無ければ 404。
     - アプリが言う「店の場所」は信じない（ごまかし防止）。
     - タイルの読み取りは npm の vector-tile の部品を使う（作る人が選ぶ）。
  2. 現在地と店の距離が 50m を超えたら 403（`too_far` と距離を返す）。
     - GPS の誤差は足さない。仕様の 50m をそのまま使う。
     - アプリ側も同じ 50m でボタンを押せなくするので、ふつうは起きない。
     - **合体した店**（§4.0）は、アプリでは地図の点の位置で距離を測るので、サーバーも合わせる。`hp:` の店は、ホットペッパーの位置（`shops`）から 50m 以内なら通す。そうでなく、アプリが `map_id`（`osm:<番号>`）を一緒に送ってきたときは、`osm:` の店と同じ要領でその点をタイルから確かめ、点から 50m 以内なら通す。どちらでも外れたら 403（距離は近い方を丸めて返す）。記録は `hp:` の店 ID のまま。`osm:` の店の `shops` への書き込みは、50m を通ったあとにする（断った要求は何も書かない）。
  3. `checkins` に1行書く。その店でその日まだコインを付けていなければ `reward_day` に今日の日付を入れ、付けていれば NULL にする。部分一意の制約で、二重に付くのを止める。
  4. `reward_day` が入ったときだけ、`coin_ledger` に `checkin` 30 を書く。
  5. 店の座標から 200m 以内のセルを `fog_cells` に `source='shop_radius'` で書く（`ON CONFLICT DO NOTHING`）。
     - セルの式は前の段 §4.2 と同じ（`dLat = 25/111195`、`dLng = 25/(111195·cos35°)`、中心が円に入るセル）。
     - アプリの `cellsInCircle` と同じ結果になることを、テストで確かめる。
- **日の区切り**: N-08 は未決定なので、今回は **JST 0時** で切る（作る人の判断。変えやすいように1か所にまとめる）。
- **返すもの**: `{checkin_id, coins_awarded: 30 | 0, new_cells: [[x,y], …]}`。`new_cells` は今回新しく晴れたセルで、演出の波に使う。
- **ログ**: 現在地・距離を出さない。
- **前提**: ユーザーの `profiles` 行があること（初回設定で作られる）。無ければ 409。

### 4.4 アプリ側
**霧の状態**
- 地図を開いたときに `fog_cells` を読む（`select cell_x, cell_y`。RLS で自分の分だけ）。
- 自宅 200m のセルと合わせたものを「晴れたセル」にする。
- 晴れたセルは、今は `worldLayers.ts` の中の固定値。これを変えられる形にして、チェックインで増えたら、雲の塊を置き直して描き直す。

**お店の出し方**（`visibleShops` を変える）
- 1km 以内で、次のどちらかに当てはまるお店を出す。
  - 晴れたセルにある
  - 現在地から 50m 以内にある（霧の中でも出す）
- 霧の中の店は、50m より離れたらまた消える。

**霧の中のお店のまわりを薄くする**
- 霧のレイヤーに「薄くする場所」を最大4か所渡す。50m 以内にある霧の中の店の位置と、その濃さ（0〜1）。
- 店から半径約 35m の雲の塊を、近いほど透けさせる（透け具合は作る人の調整）。
- 濃さは、自分と店の距離で決める。50m で 0、30m 以内で最大。急に変わらないよう、少し時間をかけて動かす。
- 晴れた場所の店には使わない。

**お店のタップ**
- three.js の建物を、画面の点で当てて選ぶ（raycast）。建物のまわりの少し広めの範囲で当たるようにする。
- 選んだら、お店の板を出す。カメラは少し寄せる（zoom +0.6 くらい、easeTo）。
- 今のカメラは自分を追いかけているので、寄せても追いかけは止めない（作る人の判断）。

**お店の板**（React。下から出る）
- ジャンルの絵（シロのピンのアイコン13種。届くまでは仮の色丸）
- 店名
- 営業時間（`open` の文。長ければ省略）
- 今の距離
- 「チェックイン」ボタン
  - 50m より遠いときは押せない形にして、「あと ◯m」を出す。
  - 押したら、結果が返るまでもう一度は押せない。
  - 失敗したら板に理由を出す。遠い・通信の失敗・すでに処理中、を分ける。
- 写真を出すなら「【画像提供：ホットペッパー グルメ】」も出す。今回は写真を出さない（見本の板に写真は無い。作る人の判断）。

**演出**（§3 の A 案）
1. **紙ふぶき**: DOM か canvas で 1.2 秒。
2. **完了の帯**: 緑。「チェックイン完了」と「+30 コイン」を出す。コインが付かなかった日は「今日のコインは受け取り済み」と出す。
3. **ピンのチェックの印**: その店のピン（建物の上）。チェックインした店は、印を付けたままにする。
4. **霧の波**:
   - 返ってきた `new_cells` を晴れたセルに足す。
   - 置き直す前と後の雲の塊を比べ、消える塊と小さくなる塊を、店からの距離に合わせて時間をずらしながら、ふくらませてから縮める。
   - 試作の `fogLayerSpike.ts` と同じ仕組み（塊ごとに「変化後の半幅」と「始まる時刻」を渡す）。
   - `new_cells` が空のとき（すでに晴れていた）は波を出さない。

**クレジット**
- 地図の右下（出典の近く）に「Powered by ホットペッパーグルメ Webサービス」のリンクを、文字の形で常に出す。
- 起動時のスプラッシュの出典一覧にも足す。

**Overpass を外す**
- 外すもの: `overpass.ts`、`OVERPASS_*` の調整値、`supabase/functions/shops-overpass/`、OSM のタグで振り分ける `genre.ts`。
- お店の仮データは開発用だけという決まり（`shopSourceEnabled`）は、ホットペッパーでも残す。本番に出すのは本人の OK のあと。そのとき本番の Supabase にもキーを入れる。

### 4.5 13種の振り分け
SPEC §9 の表のとおり、上から順に判定する。ホットペッパーと一致した店はジャンルコードで、地図のデータだけの店は地図の種類（§4.0）と店名で判定する。
- ラーメン（G013）
- 寿司（和食＋店名「寿司・鮨・すし」）

## 7. 作る人に任せること
- **ホットペッパーの並び順**: 距離順かどうかを確かめる。ページを何枚まで取るか（最大3）。
- **地図の点の番号**: 地図のデータが更新されると番号が変わることがある。チェックイン済みの店は `shops` に残るので図鑑は困らない。地図の点と結びつかなくなった店の扱いは図鑑の段で決める。
- **24時間を過ぎた `shops` の行**: 表示には使わない（表示は毎回取り直した一覧）。チェックイン済みの店の行は、図鑑のために残す。図鑑を作る段で、取り直し方を決める。
- **細かい調整値**: 薄くする半径と濃さの変わり方、カメラの寄せ方、演出の時間。
- **仮の絵**: 紙ふぶきの形と色、ジャンルの仮の絵。シロの絵が届くまでのもの。

## 8. 決まっていない・確かめること
- **日の区切り（N-08）**: 今回は JST 0時。本人の決定待ち。
- **iPhone での重さ**: 霧の塊の数（約7,600）に、薄くする計算と演出が加わる。実機で確かめる。
- **本番**: 本番の Supabase にキー・関数・マイグレーションを入れるのは、本人の OK のあと。
- **お店の数**: 地図のデータが土台なので、ホットペッパーに無い店も出る（§4.0）。地図のデータに無い・名前が古い店はある（OpenStreetMap はみんなで作る地図のため）。実機で自宅まわりを見て確かめる。
- **地図の点が多すぎる地域**: 1km に数百軒ある所でも、建物で出すのは近い 40 軒まで（今の決まり）。

## 9. シロへの依頼（素材）
`handoff/to-shiro/` に1件書く。どれも「明るい昼のグルメ」、パステル、白基調、透明背景の PNG。
- **紙ふぶき**: 3〜4種の小さな形（丸・星・リボン・もぐもGO らしい食べ物の欠片）。各 64×64px。
- **完了の帯の飾り**: 帯の左に置くチェックの丸、128×128px。帯そのものは CSS で作る。
- **コイン**: グルメコインの絵、64×64px（帯の「+30」の横、のちにガチャでも使う）。
- **ピンのチェックの印**: 建物の上のピンに重ねる小さな印、64×64px。
