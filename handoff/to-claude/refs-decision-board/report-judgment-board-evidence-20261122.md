# Judgment Board Evidence — AI-driven development with coding agents

## Summary

**Verdict: Supported, but only as a visibility / triage layer on top of upstream filtering and gates — not as a volume reducer by itself. Confidence: high for the bottleneck diagnosis and for the existence of board/queue products; medium for causal claims that a board alone reduces bottleneck time.**

- **[Anthropic primary]** Anthropic's own 2026-10-16 report says human attention *is* the bottleneck, sessions wait ~80% of the time for humans, and employees responded by doing "meta-work" — building dashboards, visibility tools, an agent chief-of-staff to triage requests, and integrated dashboards — rising from 10% to 22% of sessions. That is direct first-party support for making pending judgments visible.
- **[Anthropic primary]** Anthropic's AI-native SDLC playbook (2026-08-21) does **not** propose a single judgment board by that name. It proposes the ingredients a board would display: committed artifacts as audit trail, findings **ranked by severity**, hooks that can **allow / ask / block**, a named human threshold, time-waiting-per-gate measured via telemetry, and in Stage 6 a literal **triage queue** for monitoring findings with fix-now / schedule / dismiss decisions.
- **[Product facts]** At least six shipped products implement a queue/board of exactly this shape: Claude Code agent view (`Needs input / Ready for review` on top), OpenAI Codex app (review queue + Triage inbox), Devin Desktop Agent Command Center (Kanban: in progress / blocked / ready for review), Cursor Cloud Agents dashboard, Graphite PR Inbox + Merge Queue, and Linear Inbox + Triage. Details and limits in §2.
- **[Third-party research / counter-evidence]** Telemetry (Faros 2026, 22,000 devs) and DORA 2025 show review queues swelling under AI adoption — median time in review +441.5%, time to first review +156.6% — and Anthropic's own containment work shows per-action approval collapses into rubber-stamping (93% approved). A board that merely lists *more* items to approve will inherit that fatigue. The sources that work pair the board with upstream reduction: sandboxing cut prompts 84%, auto-mode classifiers filter safe actions, SDLC hooks/skills and `REVIEW.md` caps (e.g. max 5 nits) cut noise before it reaches a human.

## Findings

### 1. Anthropic's own internal visibility tooling

#### 1a. "How employment is changing at Anthropic" — Anthropic Economics, 2026-10-16 — [Anthropic primary]

Source: Wilmers, Catipon, Massenkoff & McCrory, https://www.anthropic.com/research/employment-at-anthropic — read via web index fetch 2026-11-22. Canonical URL given in mission; fetched URL carried a `?ref=` parameter.

Key findings box (verbatim framing):

> "This acceleration makes human attention the bottleneck for agent output. Even among non-technical employees, reading all the output of their Claude agents would take half their work week. In response, employees turn to 'meta-work,' of building visibility tools and monitoring agent pipelines."

Exact passages requested:

- **Army of Claudes / bottleneck:**
  - "One engineer described work as facing 'an army of Claudes, with every one asking for my attention.'"
  - "Amid this model-driven acceleration, human attention is a constant bottleneck. In interactive, multi-turn sessions, the vast majority of agents' session time is not spent working at all, but spent waiting. … Claude sessions amount to around 80% idly waiting for human input. As one engineer put it, people are 'bottlenecking the agents.'"
  - Babysitting analogy on undifferentiated urgency — directly relevant to why priority/risk sorting matters: every agent voices concern "with the same level of concern" whether trivial ("juice box") or serious ("sliced their finger and is bleeding") — i.e. agents do **not** self-prioritise for the human.

- **Dashboards monitoring fleets:**
  - "Dashboards monitor fleets of agents operating across the company. But personal assistant agents also monitor employee calendars and messages, scheduling, sending to-do lists accumulated from incoming messages, and automatically briefing employees…"
  - Sales example: "a sales representative designed a custom dashboard and pipeline tailored to their work: 'a build like this was out of my wheelhouse… But I built this probably in three to four hours, just iterating on it.'"

- **Agent chief of staff to triage / integrated dashboards:**
  - "One engineer set up an agent chief of staff to triage agent requests. Another wrote a performance review for their Claude team… Recruiters built integrated dashboards with agents surfacing problems and initiating actions."
  - Parallel non-engineering examples in same report: a finance manager "built a purchase request review agent"; an executive assistant built a scheduling/email-triage agent and moved to "chief of staff" tasks; a lawyer built automations to "scan risks and opportunities, triage legal questions and take first passes" at copy.

- **Meta-work share — before/after:**
  - "Figure 7 shows that this kind of meta-work leapt from **10% of the average employee's interactive Claude sessions in fall 2025 to 22% in spring 2026**. Much of this rise was due specifically to agent management: writing specs for multi-agent runs, looping one agent to review another's output, and monitoring pipelines."
  - Standing instructions as part of same shift: "Written standing instructions for agents grew from a few hundred in July 2025 to 8,500 a year later."
  - Scale context: "By August interactive AI agent hours outnumbered employees' six to one"; code commits per engineer ~5× in six months.

- **Visibility of human work itself:**
  - "Private work, in unlogged meetings and direct messages, is invisible, confusing and discouraged in an AI-heavy workplace" and "The need to feed AI context requires observability of human work and decisions." / "Keeping human work visible across the company ensures autonomous agents reason from fresh context."

**What this does / does not prove:** It proves Anthropic employees *spontaneously built* dashboards/triage/visibility tooling and Anthropic frames that as the adaptive response to a human-attention bottleneck. It does **not** describe a single company-wide "judgment board" product, a priority-sorted queue UI, or a measured effect of a board on wait time. Mark that specific design as **not confirmed** in this source.

#### 1b. "The AI-native SDLC playbook" — Louis Claxton (Applied AI), claude.com blog, 2026-08-21 — [Anthropic primary]

Canonical: https://claude.com/blog/the-ai-native-sdlc-playbook — full text read 2026-11-22 via Anthropic-official-resources mirror at https://github.com/0langa/anthropic-official-resources/blob/HEAD/content/claude.com/blog/the-ai-native-sdlc-playbook/index.md (author/date confirmed on page: Louis Claxton, August 21, 2026) and Claude Academy course pages, e.g. https://academy.claude.com/courses/ai-native-sdlc-playbook/ai-in-the-pr-review-loop

Relevant to visibility / monitoring / gates / queues:

- **Diagnosis identical to §1a:** "The bottleneck moves to the steps to the left and right of the build phase. This is mainly plan, review/test, and deploy, which still run at human speed." Security worked example: "Security teams are sized for human output, so when agents multiply code output, **either the review queue builds or code ships under-reviewed**."
- **No single board proposed; instead a chain of pre-digested artifacts:** Each stage commits an artifact the next stage reads (`intent.md → spec.md → plan.md → diff+tests → PR with review findings → incident record`); "The chain of commits is also the audit trail: who asked for what, what the agent produced, and who approved it." "Human attention concentrates at the gates, reviewing what the agent flagged rather than starting each stage from scratch."
- **Pre-digestion + proposed ranking (closest analogue to "evidence + proposed verdict"):**
  - Deploy / PR review: "All PRs get an identical set of review passes, **with findings ranked by severity**. Human attention moves up a level, to whether the change does what the plan intended and whether the risk is acceptable." Human review "reserved for regulated and critical code."
  - `REVIEW.md` defines passes (bugs, security, compliance vs spec/plan), defines "what counts as Important as opposed to a Nit, and what to skip," and caps noise: worked example "Report at most five nits per review; summarize the rest as a count" and "Do not report: Generated files… and anything CI already enforces."
  - Severity as machine-readable gate input: "A platform engineer who wants to gate merges on findings can read the **severity counts that the check run publishes as a machine-readable tally**." Findings alone do not approve/block; "branch protection still requires approval from a code owner."
- **Hooks as approval gates — allow / ask / block:**
  - "A hook can also **ask, pausing the action until a specific person approves**, which is what release gating needs." Platform engineer "expresses each gate as a hook, a script that runs before Claude acts that can allow, ask, or block." "A block should explain itself, so when a hook stops an action the reason and the route to approval appear in Claude's output."
  - **Escalation-age / wait visibility is explicitly a metric:** Hooks play leading indicator = "**Time spent waiting on each approval gate**. Every hook decision is written to the OpenTelemetry export with a timestamp and an allow or block verdict, so the wait is visible per gate."
  - Warning against putting asks too early: ask-hooks belong at Deploy, because an approval prompt during Build "puts a person back on the critical path" (summarised in secondary wiki at https://jc-aiwiki.pages.dev/claude-ai/ai-native-sdlc-playbook — treat wording beyond the primary text above as secondary).
- **Stage 6 Maintain — an explicit triage queue:**
  - "Stage 6: Maintenance runs headless, with an **independent confidence gate between stages**, a deterministic check or an adversarial reviewing agent, deciding whether the previous stage's output continues or is **escalated to a human**."
  - Response tiers in `bands.yaml`: 1σ = log only, 2σ = invoke Claude read-only to diagnose, 3σ = Claude may act only by opening a PR into the review gate or triggering a pre-approved runbook.
  - Queue handling: "The service owner or on-call engineer **triages the queue**, routing product-facing findings to the product owner. **Fix now, schedule, or dismiss. Dismissals tune the bands and help to reduce noise**." Leading indicator = "Time from band breach to an `intent.md` **in the triage queue**"; lagging = share of findings that become merged fixes.
  - Security scans analogue: each finding "validated before it is reported and **a confidence rating attached**"; triage = "Dismiss with a reason, so the dismissal is recorded and the same finding does not return as new."

**Assessment:** Strong support for the board's *contents* (severity, evidence artifact, confidence, gate wait-time, dismiss-with-reason) and for gating upstream. **Not confirmed:** any dashboard/queue UI, single-pane view, or priority-sorted board in this playbook — the system of record it prescribes is git commits + PRs + telemetry exports, not a board.

### 3. Evidence for or against a prioritised decision queue

#### For — queue is the bottleneck, and making wait/priority visible is the first fix

- **[Third-party telemetry] Faros AI, *AI Engineering Report 2026: The Acceleration Whiplash* (analysis as of March 2026)** — 2 years, 22,000 developers, 4,000+ teams. Under high AI adoption: median time to first PR review **+156.6%** (pure queue wait, before anyone reads), average time in review +199.6%, median time in review **+441.5%**, PR size +51.3%, bugs/PR +54%, **+31.3% more PRs merged with no review at all**. Interpretation offered by Faros itself: code arriving "is often not review-ready" — i.e. the queue is where unfinished work piles up. Sources: https://pages.faros.ai/hubfs/AI_Engineering_Report_2026_The_Acceleration_Whiplash_Faros.pdf and https://www.faros.ai/blog/ai-code-quality-senior-engineer-review-burden
  - Caveat (from critical reading, https://tim-schipper.nl/en/blog/ai-code-review-bottleneck ): the 441.5% blends queue wait + reading + rework rounds; the cleaner queue signal is +156.6% time-to-first-review. Figures are correlations across teams moving low→high adoption, not a controlled experiment, and are often misattributed to DORA.
- **[Third-party telemetry, via secondary synthesis] LinearB 2026 Software Engineering Benchmarks** — 8.1M PRs, 4,800 orgs: AI-assisted PRs wait 4.6× longer for pickup; agentic PRs sit idle 1,055 min before opening vs 201 min unassisted; AI PRs accepted 32.7% vs 84.4% human. Cited in https://infragap.com/ai-code-review-bottleneck/ — **primary LinearB report not opened; treat as secondary**.
- **[Research programme] DORA, *State of AI-assisted Software Development 2025* (Sept 2025)** — ~5,000 professionals, 100+ hrs qualitative. "AI's primary role is that of an **amplifier**. It magnifies the strengths of high-performing organizations and the dysfunctions of struggling ones." AI adoption now correlates with higher throughput **and** higher delivery instability; 90% use AI, 30% report little/no trust in AI-generated code. Implication: a board amplifies whatever process exists — it does not fix a weak one. Source: https://services.google.com/fh/files/misc/2025_state_of_ai_assisted_software_development.pdf?utm
- **[Engineering practice — code review as queueing]** Synthesis at https://aicodereview.cc/blog/how-to-make-code-reviews-faster/ (verified 2026-10-19 per page): "Review speed is almost never a reading-speed problem. It is a queueing problem." In its sample of 2,189 PRs, median time-to-first-review 8.7h but p90 212h; median PR spent 52.7% of open-to-merge life waiting for first human. Prescription: measure wait segments separately, fix queue before reading speed. Also cites Google Engineering Practices (max 1 business day to first response) and SmartBear/Cisco (200–400 LOC optimal, defect detection drops past 400).
- **[SRE / incident practice] PagerDuty Intelligent Triage** — vendor claim, treat as vendor evidence: grouping related alerts + adding context (has it happened before, how resolved, blast radius, who is working on it) was marketed (2019 launch) as cutting coordination time from ~80 min average to as little as 5 min; current platform page claims 70% faster resolution for customers (methodology not inspected). The transferable pattern is not the number but the design: **group duplicates, enrich with history/context, route to right responder** — exactly "pre-digested with evidence." Sources: https://www.pagerduty.com/newsroom/intelligent-triage-dashboards/ (2019) and https://www.pagerduty.com/platform/incident-management/
- **[Practitioner / mission-control pattern]** Multiple independent practitioner builds converge on the same question as their dashboard headline — "what's happening right now, and **what needs me?**" e.g. Daniel Moya's Claude Dashboard / swarm stack, https://www.danimoya.com/blog/running-an-ai-coding-swarm-across-my-servers ; Open Swarm's bet summarised as "the bottleneck is supervision, not spawning: it put every agent on one canvas, funneled every tool-use request into a single approval workflow" https://m.tomrochette.com/agents/orchestration/open-swarm/ (project pivoted proprietary Oct 2026). A research synthesis (2026-08-23) summarises field consensus: human reviewer caps agents per person at observed 2–5, and "'which of my N sessions needs me right now' is documented as an unsolved pain from mid-2025 onward" https://github.com/almazko/episcope/blob/HEAD/docs/multi-agent-research.md — all **third-party / practitioner, not peer-reviewed**.

#### Against / limits — a board alone does not reduce volume; upstream gating matters more

- **[Anthropic primary — strongest counter-evidence] Anthropic, "How we contain Claude across products," 2026-05-25** — https://www.anthropic.com/research/how-we-contain-claude?ref=runtimewire
  - "Our telemetry showed **users approved roughly 93% of permission prompts. The more approvals a user sees, the less attention they pay to each**, becoming over time much less diligent in their supervision. We recently built Claude Code auto mode, which automates safer approvals in order to reduce this approval fatigue."
  - Anthropic's chosen fix was **not** a better approval list: it was (a) a classifier (auto mode "catches roughly 83% of overeager behaviors before they execute") and (b) containment — OS sandbox (Seatbelt/bubblewrap) that, per secondary summaries of the same post, **cut permission prompts by 84%** by making safe actions never need to ask. Lesson for a judgment board: if every item reaches the board, the board becomes the rubber stamp.
- **[Anthropic primary — SDLC playbook, same point]** Noise must be capped upstream: `REVIEW.md` caps nits at 5, excludes CI-enforced and generated files, skills make violations "rare" and hooks make them "close to impossible"; Stage 6 dismissals "tune the bands and help to reduce noise"; 1σ events are log-only and never reach a human. A board without equivalent tuning will drown in low-severity items.
- **[Third-party research synthesis] Oversight capacity is inverted-U:** escalating *more* to a fatiguing human can make the system *less* safe; reviewers agree on risk at only κ=0.52 (cited as "Oversight Has a Capacity" in https://github.com/almazko/episcope/blob/HEAD/docs/multi-agent-research.md ). **Primary paper not opened — mark as secondary citation only.**
- **[DORA, above]** No relationship found between AI adoption and reduced friction/burnout in DORA 2025 — visibility tooling alone should not be expected to relieve the human; workflow/platform quality is the moderating variable.

**No source found** that experimentally compares "board vs no board" for agent supervision (randomised or controlled). All board-efficacy evidence is indirect: queue-wait telemetry, incident-triage vendor claims, and practitioner convergence. Mark causal efficacy as **not confirmed** by direct study.

### 4. Bottom line synthesis — conditions under which evidence supports a judgment board on top of gates

Supported, if built as Anthropic + Linear + PagerDuty patterns suggest:

- **Who builds / owns it:** Employees closest to the work built the Anthropic examples themselves (sales rep in 3–4 hrs, recruiters, finance manager) — bottom-up, domain-specific boards worked; the SDLC playbook assigns system-level pieces to platform/tech leads (`REVIEW.md` policy, hook gates, bands config). A board needs a named rotating owner (Linear's Triage captain / responsibility, syncable to on-call) — unowned queues in every source decay into backlogs.
- **What each item must carry (evidence-backed checklist):**
  1. **Severity / priority, mandatory** — SDLC findings ranked by severity + machine-readable severity tally; Linear can require priority before leaving triage. Without this, Anthropic's babysitting problem recurs: all items shout equally.
  2. **Evidence artifact, pre-digested** — the committed artifact (intent/spec/plan/diff + test/eval output), a one-line summary (Claude agent view's Haiku summary + peek), and for monitoring items the anomaly + evidence in `intent.md` form. PagerDuty pattern adds: has this happened before / how was it resolved.
  3. **Proposed verdict / confidence** — SDLC Stage 6 confidence gate + Claude Security confidence rating per finding; Codex/Code Review severity counts. Item should arrive with a recommendation (fix now / schedule / dismiss; approve / request changes), not raw output — Anthropic data show raw output alone would consume >½ the work week to read.
  4. **Escalation age / wait time** — SDLC hooks play explicitly measures time waiting per gate via timestamped telemetry; Graphite shows queue position + ETA; Linear SLAs make age actionable. Age must be visible and breach a tier (log → diagnose → act) rather than just accumulate.
  5. **Dismiss-with-reason + feedback loop** — SDLC: dismissals recorded, tune bands/`REVIEW.md`/`CLAUDE.md`, so the same low-value item does not return as new. Without this loop the board's volume only grows.
- **What the board does NOT solve (explicitly):**
  - **Volume.** It does not reduce how much agents produce. Volume is reduced upstream: sandboxing (−84% prompts), auto-mode classifiers, hooks/skills, nit caps, PR-size limits, deterministic checks in CI. Faros: even with 25% of PRs now AI-reviewed, review time still rose ~200%.
  - **Rubber-stamping.** A board that surfaces every action replicates the 93% approval-fatigue failure. Only risk-tiered surfacing (safe = auto, risky = human) preserves judgment.
  - **Instability / quality.** DORA: AI raised throughput and instability together; a board does not substitute for evals, tests, rollback paths, or a healthy platform.
  - **Coordination / judgment itself.** Anthropic employees' meeting time rose 16–20% even as dashboards spread; "human convening and decision-making and governance" remained face-to-face work. The board routes judgment; it does not make it.
