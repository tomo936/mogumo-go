# 個人開発課題 第二案（AI 駆動開発の体験）

> 第一次案への意見ありがとうございました。いただいた3点（Web にしたい／案1と案5を合わせたい／地図の情報をどこまで取れるか）を受けて、Web で「霧晴らし × クエスト」の5案を作りました。この中から1つ選んでください（混ぜても構いません）。

## 1. 第一次案から変わったこと

| 項目 | 第一次案 | 第二案 |
|---|---|---|
| 形 | Android か Web | **Web**（スマホのブラウザで遊ぶ） |
| テーマ | 5つの別々の案 | **霧晴らし（案1）× デイリークエスト（案5）を土台にして、芯の置き方を5通りに変えた** |
| 地図の範囲 | 書いていなかった | **全国はやらない。範囲を決めること自体を要件定義の最初の仕事にする**（下の 3章） |

ねらい・進め方（要件定義 → 基本設計 → 詳細設計 → 実装 → 検証 → 振り返り）・エージェントを分けて組むこと・AI を Sandbox の中で動かすこと・苦労日誌は、第一次案のままです。

## 2. 「最寄りだけ試して苦戦した」は、もう苦労日誌の1件目です

- 試したのはいつか・何を使ったか（どの API・どのサイト）・どこで詰まったか・どう止めたか を、今のうちに書き残してください
- 発表で「最初は全国の地図を取ろうとして詰まった → 範囲を絞るのが要件だと気づいた」と話せれば、それだけで要件定義の学びを1つ語れます

## 3. 地図の情報はどこまで要るか（懸念へのこたえ）

**全国は要りません。** このアプリで要るのは「自分が歩ける範囲のお店」だけです。

- 範囲の例: 「会社の周り 1km」「自宅の周り 1km」。これを決めるのが要件定義の最初の仕事
- お店の情報は OpenStreetMap の Overpass API で、範囲（四角か円）を指定して1回問い合わせれば取れる見込みです（amenity=restaurant・cafe・fast_food など）。1km 四方なら数十〜数百件の規模
- 取った結果は JSON にしてアプリに同梱すれば、遊ぶたびに API を呼ばなくてよい。データの更新はたまに手で
- 地図の絵（タイル）は Leaflet ＋ OpenStreetMap のタイル。出典の表示と、アクセスの頻度の決まりを守ることも要件に入れる
- **注意: データは汚い。** 店の名前が無い・ジャンル（cuisine）が無い・閉店した店が残っている、などが普通にある。どう扱うかも要件

### 地図はどこまで正確である必要があるか（炭田さんが選ぶ）

Google マップほど正確である必要があるかは、決まっていません。**正確さと費用・手間の釣り合いを決めるのも要件定義です。** 下の候補から選び、選んだ理由を要件定義書に書いてください。

地図には「背景の絵（道や建物）」と「お店のデータ」の2つがあり、別々に選べます。

| 候補 | 背景の絵 | お店のデータ | 費用・手間 | 気をつけること |
|---|---|---|---|---|
| OpenStreetMap（Leaflet＋OSM のタイル、Overpass API） | ○ | △ 地域で差が大きい（名前・ジャンルの欠け、閉店した店が残る） | 無料・API キー不要 | 出典の表示とアクセスの頻度の決まりを守る |
| 無料のベクターデータを自分で配る（OSM 由来のデータを1つのファイルにして、GitHub Pages などに置く。例: Protomaps） | ○ 色や見せ方を自由に変えられる（霧の表現と相性がよい） | お店は別に用意する | 無料。範囲を切り出して置く手間がある | 範囲を絞れば軽い |
| 国土地理院の地図（地理院タイル・ベクトルタイル） | ◎ 道・建物は正確 | ✕ お店のデータは無い | 無料・API キー不要 | 出典の表示が要る。お店は OSM などと組み合わせる |
| Google マップ（Maps JavaScript API・Places API） | ◎ | ◎ 店名・ジャンル・営業時間がそろう | 無料枠はあるが、API キーと課金の登録（カード）が要る | 取ったデータの保存・加工に規約の制限がある。使いすぎると課金される |

- 「会社の周り 1km のお店が、だいたい合っていればよい」なら OSM で足りるかもしれません。まず自分の範囲で Overpass API を1回呼び、何件出るか・どれくらい欠けているかを見てから決めるのがおすすめです（その結果も苦労日誌の材料）
- お店が足りなければ、「自分で店を足せる」機能を付けるのも1つの答えです

### 課題は休日にやるので、確かめるのは「自宅の周り」になりがち

会社の周りを範囲にすると、外を歩いて確かめられるのが平日の昼休みだけになります。最初の範囲を自宅の周りにするか、両方にするかも決めどころです（案D はここを芯にしました）。

## 4. Web でやるときに先に知っておくこと（発掘の種）

| こと | 中身 | 手の候補 |
|---|---|---|
| **スマホで位置を取るには HTTPS が要る** | ブラウザの位置情報は HTTPS か localhost でしか動かない。PC で立てたローカルサーバーにスマホから http でつなぐと、位置が取れない | ① 静的なページにして GitHub Pages などで公開する（HTTPS になる）② 開発中は PC のブラウザの「位置を偽装する機能」（Chrome の開発者ツールの Sensors）で試す |
| **画面を消すと記録が止まる見込み** | ブラウザは、画面を消したりほかのアプリに切り替えたりすると位置を取れなくなるのが普通。歩いた道を全部は記録できない | 「アプリを開いている間だけ記録する」と割り切る／画面を消さない仕組み（Wake Lock）を使う／お店に着いたときだけ記録する |
| **記録をどこに置くか** | サーバーを作らないなら、ブラウザの中（localStorage など）。機種変更やキャッシュの削除で消える | 消えてよいことにする／書き出し・読み込みのボタンを付ける |
| **iPhone と Android で振る舞いが違う** | 位置の許可の出し方や精度がブラウザごとに違う | 使うスマホを1つに決めて、受け入れ基準をそのスマホで書く |

### AI と一緒に作るとき、API キーの扱いは単純ではない

Google マップなど API キーが要るものを選ぶ場合は、キーの扱いも要件と設計に入れてください。AI と一緒に作ると、次のことが起きやすくなります。

- **AI がキーをソースに直接書き、そのままコミット・MR にする。** 一度 GitHub に上がると、消しても履歴に残る。公開リポジトリなら数分で拾われることもある
- **AI はキーの入ったファイル（.env など）も読める。** 読んだ内容は会話に残る。「読ませない」なら、読ませない仕組み（置き場所・Sandbox の設定）が要る
- **ブラウザで動くページに入れたキーは、誰でも見られる。** 静的なページでは隠せない。隠せない前提で、使える場所（自分のサイトの URL だけ）や使える API を絞る制限をキーにかける
- **AI のレビュー役も見落とすことがある。** 「キーが入っていないか」を機械で検査する仕組み（コミット前の検査など）を自分で用意するのが確実

どう守ったか、どこで AI が危ないことをしかけたかは、基本設計書（非機能要件）と苦労日誌に残してください。発表でも「AI に任せてはいけない所」の具体例になります。

サーバーを作らない形（静的なページ＋ブラウザの中の記録）なら、HTTPS の問題も「公開すれば済む」に寄せられます。ただし公開先にほかの人が来ても困らない作りにすること（自分の記録はブラウザの中だけにある、など）。

## 5. 第二案（5案）

5案とも土台は同じです: **地図が霧で覆われている／歩いた所と行ったお店の周りが晴れる／毎日クエストが出る。** 違うのは「何を一番の楽しさにするか（芯）」です。

### 案A 霧を晴らすクエスト（芯: クエストの報酬が霧を晴らす）

- 種: 「会社の周りのお店を開拓するのが楽しくなるアプリがほしい。毎日ちょっとした目標があるといい」
- イメージ: 歩くだけでも霧は少し晴れるが、クエストを達成すると大きく晴れる（例「まだ行っていない喫茶店に行く → その店の周り 200m が晴れる」）
- スクショ: 霧の中に、クエストで晴れた丸がいくつも浮かぶ地図
- 発掘の種: 晴れる大きさ／「行った」の判定（店の前を通っただけで達成か）／クエストが出せない日（近くに条件の店が無い）

### 案B 霧の向こうのお題（芯: クエストの行き先が霧の中に隠れている）

- 種: 「新しいお店に行くきっかけがほしい。行くまで何の店か分からないとわくわくする」
- イメージ: クエストは「霧の中、北東 400m に未訪問のお店がある。ジャンルはカレー」のようなヒントだけ。近づくと霧が晴れて店名が出る
- スクショ: 霧の中にヒントの印がある地図と、晴れて正体が分かった後の地図の2枚
- 発掘の種: ヒントをどこまで出すか／近づいたの判定の距離（位置の誤差は数十m ある）／ジャンルが分からない店をお題にするか

### 案C 小さく確実に1周（芯: 範囲と機能を最初から絞って、進め方の体験を厚くする）

- 種: 「会社の周り 1km だけでいい。行ったお店が地図で分かって、毎日1つお題が出れば十分」
- イメージ: お店のデータは最初に1回取って同梱。霧はマス目。クエストは1日1つ。サーバー無し
- スクショ: マス目の霧と開拓率（○%）
- ねらい: 作る量を減らして、要件定義・設計・AI の自律実装・検証の1周を確実に回す。余った時間で案A か案B の要素を足す
- 発掘の種: 開拓率の分母（範囲の中のマス数か、お店の数か）／マスの大きさ

### 案D 2つの島（芯: 会社の周りと自宅の周りを別々に開拓する）

- 種: 「平日は会社の周り、休日は家の周りでお店を開拓したい」
- イメージ: 地図の中に霧の「島」が2つある。平日は会社の島、休日は自宅の島のクエストが出る。島ごとに開拓率
- スクショ: 2つの島の開拓率を並べた画面
- 発掘の種: 島の範囲を誰がどう決めるか（設定画面か、固定か）／島の外に出たとき／平日と休日の切り替え（祝日は？）／自宅の位置という個人情報をどこに置くか
- 向き: 休日に作業する炭田さんが、自宅の周りで検証できる

### 案E 5週間の開拓記（芯: 変化の記録。発表のスクショから逆算する）

- 種: 「どれだけ開拓したかを、あとで振り返れるようにしたい」
- イメージ: 霧晴らしとクエストに加えて、日ごとの開拓の記録を残す。「1週目 → 5週目」の霧の地図を並べて見られる
- スクショ: 始めた日と最後の日の地図を並べた画面（発表の「成長」の話にそのまま重なる）
- 発掘の種: 何を記録するか（晴れたマス・行った店・達成したクエスト）／記録が消えたとき／いつから記録を始めるか（作っている途中のデータをどうするか）
- 注意: 記録を見せるには、作り始めの早い段階で記録の機能を入れておく必要がある。後から作ると5週分のデータが無い

### 比べると

| 案 | 冒険感 | スクショの映え | 規模 | 要件の発掘の濃さ |
|---|---|---|---|---|
| A 霧を晴らすクエスト | ◎ | ◎ | 中 | ○（達成の判定） |
| B 霧の向こうのお題 | ◎ | ○（2枚で伝わる） | 中 | ◎（ヒント・位置の誤差） |
| C 小さく確実に1周 | ○ | ○ | **小** | ○ |
| D 2つの島 | ○ | ○ | 中 | ◎（範囲・個人情報） |
| E 5週間の開拓記 | ○ | ◎（成長の比喩） | 中〜大 | ○ |

迷ったら、**案C で始めて、余った時間で A・B・E の要素を1つ足す**のが安全です。規模で失敗すると、検証と振り返りまで届かず、発表の材料が残りません。
