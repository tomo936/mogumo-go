# 霧（3Dの雲の海）とお店の3D模型を地図に組み込む — 設計

日付: 2026-11-06 ／ 工程: PLAN-cycle1 の手順4「お店ピン → チェックイン → 霧」の前半

## 1. ねらい
- 地図の画面を、もぐもGO らしい見た目にする。霧（もこもこの雲）に覆われた町の中で、晴れた場所にだけお店が建物として現れる。
- 試作（`art/prototypes/`）で決めた見た目と置き方を、アプリの本物の作り（テスト付き・クリーンアーキテクチャ）に移す。
- ホットペッパーの API キーが届く前でも、13種類のお店が町に並ぶところを実機で確かめられるようにする。

## 2. やること・やらないこと
**やること（この設計の範囲）**
1. 霧のグリッド（25m のセル）と「晴れたセルの集まり」を計算する仕組み。
2. 霧の見た目: 雲の海の模様（シロの素材）＋3Dの雲。晴れた場所に穴があく。
3. 自宅のまわり 200m を、アプリを開いたときから晴れた状態にする（端末の中だけで計算）。
4. お店のデータを Overpass（OpenStreetMap の検索窓口）から取る。現在地から 1km 以内。
5. お店のジャンルを13種類の建物に振り分ける。
6. 晴れた場所にあるお店を、3Dの建物で道路向き・実際の建物に合わせて置く。
7. three.js を依存に加える（3Dの雲と建物の描画）。

**やらないこと（次の段以降）**
- 本物のチェックイン（Edge Functions、checkins・fog_cells への書き込み）。ホットペッパーと一緒に次の段で作る。
- サーバーの fog_cells を読むこと（書き込みが無い間は常に空なので、今は作らない）。
- 自宅→店のルートの帯、町の制覇、気配（ヒント）、クエスト、図鑑。
- お店の上のピン（S16）。13ジャンルのアイコン素材がまだ無いため。シロへの依頼として出す（9章）。
- タップしたときの細かい模型（店内の作り込み）。
- アバターのスプライト（男の子8方向は届いているが、別の作業）。

**してはいけないこと（失敗とみなす）**
- 自宅の位置がサーバーや外部に漏れること。自宅まわりのセル・自宅中心の検索範囲を外へ送らない。
- iPhone で地図の動きがカクつくこと（目安: 画面に出す三角形の数を合計 約60万以内）。
- 位置が1回変わるたびに React の再描画が走ること（今の MapView の方針を守る）。

## 4. 作り方
### 4.1 フォルダと責務（クリーンアーキテクチャ）
```
src/fog/
  domain/  grid.ts（セル番号 ⇔ 緯度経度）, clearing.ts（円で晴らす・晴れ判定）, cloudSpots.ts（雲を置く場所の計算）
  infra/   cloudLayer.ts（three.js の雲のレイヤー）, seaLayer.ts（模様と穴の canvas）, cloudModels.ts（glb 読み込み）
  ui/      useFog.ts（MapView から呼ぶつなぎ）
src/shops/
  domain/  genre.ts（タグ → 13種）, placement.ts（道路向き・輪郭合わせ）, visibility.ts（晴れた場所の店を選ぶ）
  infra/   overpass.ts（取得・変換）, mapFeatures.ts（地図のタイルから道路・建物を取り出す）, shopLayer.ts（three.js の建物のレイヤー）
  ui/      useShops.ts
src/assets/shops/<種類>.glb, src/assets/fog/cloud{1,2,3}.glb
```
- domain は純粋な TypeScript（three・MapLibre・fetch を import しない）。単体テストの中心。
- three.js の扱いは infra に閉じる。ui は MapView に「レイヤーを足す・データを渡す」だけ。
- 霧とお店で three.js のレンダラーを共有するかは作る人の判断（同じ GL を使う2つのカスタムレイヤーでもよい）。

### 4.2 霧のグリッド
- セル: 地球全体で固定の原点・固定の刻み（D-06）。**刻みは緯度方向 25m、経度方向は北緯35度での 25m を固定の角度で使う**（`dLat = 25 / 111195`、`dLng = 25 / (111195 × cos 35°)`）。`cell_x = floor(lng / dLng)`, `cell_y = floor(lat / dLat)`。日本の中では 1セルがおよそ 23〜27m 四方になる（私の判断。サーバーの fog_cells もこの式に合わせる）。
- 晴れたセルの集まり = 自宅 200m の円に中心が入るセル（今回）＋将来のサーバー分・ルート分の和。
- 晴れ判定はセルで行う（店の点が晴れたセルにあれば「晴れた場所の店」）。

### 4.3 霧の描画
- **模様と穴**: 現在地を中心に一辺 3km の canvas に模様を敷き（1枚 約320m）、晴れたセルの所をやわらかい縁でくり抜いて、地図の上に貼る（試作 `fog.ts` の assetCanvas）。現在地が中心から 700m 以上離れたら作り直す。晴れたセルが変わったときも作り直す。
- **3Dの雲**: 霧のセルに、約60m おきに雲を置く。向き・大きさ・種類・高さは **セル番号から決まる乱数**（作り直しても同じ場所に同じ雲が出る）。晴れた場所に近いほど低く小さく、晴れた場所から 45m 以内には置かない。約300m 四方の区画ごとにまとめ、画面に入る区画だけ描く。
- 雲の数の上限: 現在地から 1.5km まで。

### 4.4 お店のデータ（Overpass、仮）
- 問い合わせ: 現在地から 1km の円の中の `amenity=restaurant|cafe|fast_food|bar|pub|ice_cream` と `shop=bakery|confectionery|pastry`。`name` があるものだけ。node と way（way は中心点）。
- **自宅を中心に問い合わせない**（問い合わせの中心は現在地。自宅の近くにいるときも「現在地」として送るだけで、自宅であることは伝わらない）。
- 取り直し: 前回の中心から 500m 以上動いたとき。同時に1本まで。失敗（429・タイムアウト）は少し待って1回だけやり直し、だめなら「お店を読み込めませんでした」の帯を出す。
- 13種への振り分け（私の判断。ホットペッパーの表を OSM のタグに読み替え）:
  | 建物 | 条件（上から順に判定） |
  |---|---|
  | ラーメン屋 | cuisine に ramen、または名前に「ラーメン・らーめん・拉麺・中華そば」 |
  | 寿司屋 | cuisine に sushi、または名前に「寿司・鮨・すし」 |
  | そば・うどん屋 | cuisine に soba・udon・noodle、または名前に「そば・蕎麦・うどん」 |
  | カレー屋 | cuisine に curry・indian・nepalese、または名前に「カレー」 |
  | 焼肉屋 | cuisine に bbq・barbecue・yakiniku・korean |
  | 中華料理屋 | cuisine に chinese |
  | 洋食・イタリアン | cuisine に italian・pizza・french・western・steak・spanish |
  | 和食屋 | cuisine に japanese・tonkatsu・tempura・kaiseki・teishoku・yakitori 以外の和食 |
  | 居酒屋 | amenity=bar・pub、または cuisine に izakaya・yakitori |
  | スイーツの店 | shop=confectionery・pastry、amenity=ice_cream、cuisine に cake・dessert・crepe |
  | パン屋 | shop=bakery |
  | カフェ | amenity=cafe（上のどれでもない） |
  | その他（謎の気配） | 上のどれでもない（ファストフードの多くもここ） |
- Overpass のデータは OpenStreetMap（ODbL）。出典はすでにスプラッシュ・「出典」ボタンの © OpenStreetMap で示している。
- ホットペッパーに替えるときは `overpass.ts` だけを差し替える（domain の型 `Shop {id, name, lat, lng, kind}` は同じ）。

### 4.5 お店の建物
- 表示するのは「1km 以内」かつ「晴れたセルにある」店だけ。
- 置き方は試作 `art/prototypes/map-shop-placement.ts.txt` の規則を domain に移す（入力: 店の点・まわりの道路の線・建物の輪郭（どれも現在地基準の m）→ 出力: 中心・正面の向き・大きさ）。道路と建物は地図のタイル（openmaptiles の transportation と building）から infra が取り出す。
- 置き方の計算は、店ごとに、その場所のタイルが読み込まれてから1回だけ行い、結果を覚えておく（毎コマ計算しない）。
- 模型は13種の glb。**必要な種類だけ、初めて必要になったときに読み込む**。同じ種類の店は同じ形を使い回す（three のインスタンス描画）。
- **地図用に軽くした版を作る（私の判断）**: 1種類 **1万三角形以内・400KB 以内**。Blender（この環境の作業用フォルダに入っている。`art/prototypes/blender-shops.py`・`blender-shop-jp.py` に「軽くして書き出す」手順を足す）で形を減らして書き出し、`src/assets/shops/` に置く。**この素材づくりを、お店のレイヤーより先にやる**。
- **一度に描くお店は、現在地に近い順に 40軒まで（私の判断）**。40軒×1万＝40万三角形、雲 約20万と合わせて約60万の目安に収める。
- 晴れ判定は店の点で行い、建物の一部が霧にかかってもそのまま描く（ふちは雲がやわらかく隠す。私の判断）。
- 見た目: 材質は試作どおりのマットな光（three の標準の材質＋空の光＋太陽）。輪郭線なし。

### 4.6 MapView へのつなぎ
- 今の MapView は位置と地図を ref で持ち、React を再描画しない。霧とお店もこの方針に合わせ、`map.on('load')` のあとにレイヤーを足し、位置が変わったら ref 経由で「取り直しが要るか」だけを見る。
- 自宅は `loadHome(userId)`（`src/setup/infra/homeStore.ts`）から読む。自宅が無い（初回設定前）は晴れ無しで描く。

- 実機: 開発環境（mogumo-go-dev）を iPhone 16 で開き、自宅まわりが晴れてお店が建っていること、動きが滑らかなことを確かめる。

## 11. 変更: Overpass は Edge Function を通す（2026-11-06 本人決定）
- **理由**: overpass-api.de が 2026-04-19 から、送り主を名乗らない通信（ブラウザからの直接の問い合わせを含む）を 406 で断るようになった。開発環境の iPhone でも「お店を読み込めませんでした」になり、ブラウザからは送り主の名前（User-Agent）を変えられない。
- **作り**: アプリ → Supabase Edge Function `shops-overpass` → overpass-api.de。
  - アプリは「250m に丸めた現在地」（`{lat, lng}`）だけを送る。問い合わせ文は Edge Function の中で組み立てる（任意の問い合わせを中継しない＝だれでも使える中継口にしない）。範囲は 1km 固定。
  - Edge Function は User-Agent に `mogumo-go/0.1 (+https://github.com/tomo936/mogumo-go)` を付けて問い合わせ、Overpass の JSON をそのまま返す。ログイン中の人だけが呼べる（Supabase の JWT 確認を有効のまま）。
  - **プライバシー**: 丸めた現在地が自分の Supabase を一度通る。保存しない・ログに出さない・自宅と結びつけない。自宅を送らない決まり（§2）はそのまま。
  - やり直し（429・5xx・タイムアウトで1回）と失敗時の帯は今までどおりアプリ側。
- ホットペッパーに替えるときも、同じく Edge Function を通す（キーを隠すため）。この経路がその下地になる。

## 12. 変更: 霧は絵本風 2.5D をコードで描く（2026-11-06 本人決定）
§4.3（模様の canvas と3Dの雲）を、次の作りに置き換える。
- **見た目**: 3D ではなく平面の絵本風 2.5D。もこもこの丸い膨らみが重なった雲の塊で、上が白・下側に薄い水色の影の2トーン。目標は見本の平らな雲（`art/reference/clouds-flat.png`）。
- **振る舞い**: 霧は流れない。25m セルに固定し、地図の回転・移動にそのまま追随する。
- **管理**: 晴れはセル単位（§4.2 の Cleared）。晴れ方3種（チェックインで店の周り 200m／自宅から店までの道沿い／町制覇で町全体）は、どれも晴れたセルの集まりとして渡すだけで、描く側は区別しない。
- **描画**: 画像素材は使わずコードで描く。
  - MapLibre のカスタムレイヤーに WebGL2 で直接描く。HTML の canvas を重ねる方式は、自分の位置の印とお店を隠すので使わない。地面に絵を貼る方式は、地図を回すと影の向きも回るので使わない。
  - **雲の塊の置き方**（domain、純粋な計算）: 世界に固定した六角格子（約30m おき）に、決まった乱数で少しずらして塊を置く。塊の中心が晴れたセルなら置かない。晴れたセルの中心に近いほど小さくする。小さくなりすぎたら置かない。この縮め方で、晴れの縁がもこもこになる。範囲は現在地から 1.2km 四方の半幅。700m 動いたときと晴れが変わったときに作り直す。
  - **塊の形**（シェーダー）: 横長の胴に、上の膨らみ4つを重ねた形。形は塊ごとの種で少し変える。いつも画面のほうを向けて描く。下に少しずらした所が塊の外なら水色、中なら白にする。こうすると、塊の下側にだけ影の帯が出る。
  - **重ね順**: 画面の奥から手前の順に描く（手前の塊の影が奥の塊に掛かる）。順は地図の向き（bearing）だけで決まるので、2度以上回ったときだけ並べ直す。
  - 霧は自分の位置の印とお店の建物より下に入れる。
- これで、雲海の模様の画像・3Dの雲の glb・`cloudSpots` は使わなくなるので外す。
