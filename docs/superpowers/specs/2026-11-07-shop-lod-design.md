# 見える範囲のお店を全部出す（LOD）の設計

2026-11-07。前の段: `2026-11-07-multi-shop-building-design.md`（ビル）、`2026-11-07-large-facility-design.md`（大型施設・駅）。

## 0. 言葉の言いかえ
| 言葉 | 意味 |
|---|---|
| LOD（エルオーディー） | 遠くの物を、見た目が同じで中身の軽い模型に差し替えるやり方 |
| 三角形の数 | 模型の細かさ。多いほど重い（iPhone が熱くなる・カクつく） |
| 描画の回数（ドローコール） | 1コマを描くのに、スマホの絵の担当（GPU）へ「これを描いて」と頼む回数。三角形の数と並んで重さの元 |
| まとめ描き（InstancedMesh） | 同じ模型をたくさん置くとき、1回の頼みでまとめて描くやり方 |
| 材質（マテリアル） | 模型の部品の色・つや。材質が違う部品は別々に頼む必要がある |
| 頂点の色 | 材質を分けずに、形の点そのものに色を塗っておくやり方。頼む回数を1回にできる |
| 余裕（ヒステリシス） | 切りかえの境目に幅を持たせ、境目の上を行き来してもチラつかないようにする工夫 |
| コマ（フレーム） | 画面を描き直す1回分。1秒に約60回 |

## 1. ねらい（オーナー決定 2026-11-07）
- 「重くならず、品質を落とさずに、見える範囲のお店を全部出す」。方法は LOD で了承済み。
- 発端の不具合: 経堂駅のように店が多い所で少し離れると、施設（大型施設・駅）の店の一部が40軒から外れ、施設が欠けたり、1軒の普通の店に戻ったりする。

## 2. 今の仕組み（2026-11-07 のコードで確認）
- `src/shops/domain/visibility.ts` の `visibleShops`: 現在地から 1km 以内（`SHOP_RADIUS_M`）で、晴れたセルにある店（霧の中は 50m 以内 `IN_FOG_VISIBLE_M`）を近い順に並べ、**`MAX_SHOPS`=40 軒で切る**。
- `src/map/ui/worldLayers.ts` の `refreshShops`: 上の結果を近い順に回し、まだ置き方を計算していない店だけ `placeShop`（道路向き・建物の輪郭に合わせる）と施設の形を計算して `placed` に覚える（店ごとに一度だけ）。施設の形は `facilityCache` で施設ごとに一度。そのあと `groupShops` で同じ輪郭の店を組にし、
  - 組が1軒 → 1軒の店の模型
  - 2軒以上で施設の情報あり → 大型施設・駅（`facilityLayer`）
  - 2軒以上で施設でない → ビルの模型
  - **組が1軒だと施設にならない**。40軒の上限で仲間が外れると、施設が欠けたり1軒の店に戻る原因はここ。
- 更新のきっかけ: 10m 動くごと（`SHOP_REFRESH_M`）と、地図の `idle`（動きが止まるたび）。顔ぶれ（`shownKey`）が変わったときだけ層を作り直す。
- `src/shops/infra/shopLayer.ts`: 種類ごとに glb を初めて要るときに読み、**模型の部品（材質）ごとに1つずつ** InstancedMesh を作る。つまり描画の回数は「出ている種類 × その模型の材質の数」。全部の店を1つの塊として扱うので、画面の外の店も描く対象から外れない（three の「見えない物を飛ばす」仕組みが効かない）。
- 模型: `src/assets/shops/*.glb`（13種＋building）。作り方は `art/prototypes/blender-shops.py` の `LIGHT=1 TARGET=9000`（部品を1つにつなげ、Decimate＝自動で間引く で約9,000三角形）。材質は色ごとに別（絵の画像は使っていない）。
- ピン（HTML の札）: ビル・施設だけ（`buildingPins.ts`）。1軒の店はチェック済みのときだけ ✓ の札（`checkMarks.ts`）。地図が動くたび（`move`）に全部のピンの大きさと高さを合わせ直す。
- 並行の作業: 別の作業者が worldLayers.ts で「重なる施設を1つにまとめる」修正中（`dropSharedParts` まわり）。**この設計はその修正が入った後に乗る。その部分は書きかえない。**

## 3. 決めること と 決めた案

### 3.1 出す範囲
- 40軒の上限（`MAX_SHOPS`）をやめる。`visibleShops` は条件（1km・晴れ、霧の中は 50m）に合う店を**全部**、近い順に返す。
- 安全のための上限を残す: **模型の数で 400**（`MAX_SHOP_MODELS`）。数えるのは「1軒の店の模型」と「ビルの模型（1つで1）」。**施設の店は数えない**（施設は店ごとの模型を描かないため。§3.4）。
  - 400 を超えたら、施設以外を近い順に 400 まで出す。
  - 理由: ホットペッパーは1回の問い合わせで最大 300軒（100軒×3ページ）。地図のお店と合わせても、晴れた所だけなら都心でもふつうは 300 前後に収まる見込み。400 は「データが異常に多い所で iPhone が止まらない」ための柵で、ふだんは届かない。
- 置き方の計算は今どおり店ごとに一度だけ（`placed`）。上限で外れた店も計算は覚えておき、近づいたら計算なしで出せる。

### 3.2 LOD の切りかえ
- 基準は **現在地からの距離**。地図は現在地を中心に追いかける（ズーム 16〜18・傾き 55°）ので、距離が画面上の大きさとほぼ対応する。画面上の大きさで決める案は、毎コマ計算が要り、作り直しが増えるので採らない。
- **近い店（`LOD_NEAR_M` = 150m 以内）は今の模型（約9,000三角形）、それより遠い店は軽い模型（目安 800三角形）**。
  - 目安: ズーム 17 では 1m ≒ 1 画面の点。150m 先の 16m の店は画面で 16 点ほど（傾けると奥はさらに小さい）。この大きさなら 800三角形との違いは見分けにくい。
- 詳しい模型は **最大 `LOD_MAX_DETAILED` = 40 軒**（今の上限と同じ）。店が密集していて 150m 以内に 40 軒を超えるときは近い 40 軒だけ詳しく、残りは軽い模型。これで「詳しい模型の重さ」は今より増えない。
- チラつかない工夫（余裕）:
  - 前回詳しかった店は、距離を `LOD_MARGIN_M` = 30m 近いものとして扱う（＝ 180m を超えるまで詳しいまま）。逆に軽い店は 150m を切るまで軽いまま。境目でうろうろしても行き来しない。
  - 40軒の上限での入れ替わりにも同じ扱いが効く（前回詳しかった店が少し有利）。
  - 切りかえの計算は今の更新（10m ごと・`idle`）のときだけ。毎コマは計算しない。
  - 切りかえは一瞬で差し替える（だんだん変える演出は付けない）。見た目が同じなので気づきにくい。
- ビルの模型（building）も同じ扱い（距離はビルの位置で測る）。施設の立体は今のまま（1つ数千三角形なので LOD は付けない）。
- 読み込みの順番の工夫: その種類の軽い模型がまだ読めていなければ詳しい模型で、詳しい模型がまだなら軽い模型で代わりに出す（読めた方を使う）。空白にしない。
- 大きさの基準: 模型の幅（`unit`）が詳しい版と軽い版で少しずれると、切りかえで大きさが跳ねる。Blender 側で外形の箱をそろえ（§3.3 の確認）、アプリ側は同じ種類なら詳しい版の幅を両方に使う（詳しい版がまだ読めていないときだけ軽い版の幅）。

### 3.3 軽い模型の作り方
- **案 A（採用）: `art/prototypes/blender-shops.py` に軽い版の作り方（例 `LOD=1`）を足し、元の形から作る**。
  1. 遠くでは見えない小さい部品を、つなげる前に外す（店の中の小物・細い飾りなど。大きさのしきい値は画面で比べて決める）。
  2. 平らな面をまとめる間引き（Decimate の Planar。形を崩さずに三角形を減らす）→ 足りなければ普通の間引き（Collapse）で 800 へ。
  3. 材質の色を **頂点の色** に移し、材質を1つにする（→ 種類ごとの描画の回数が 1 回で済む。§3.7）。光る窓（emission）は少し明るい色で代わりにする。
  4. 書き出し先: **`src/assets/shops/lod/<種類>.glb`**（13種＋`building`。名前は今の glb と同じ）。今の glb の読み込み（`../../assets/shops/*.glb`）はフォルダの中まで拾わないので、軽い版は別の読み込みで拾う。
  5. 外形の箱（幅・奥行き・高さ）が詳しい版と 2% 以内で合っているかを、書き出しのときに表示して確かめる。
- 案 B（採らない）: 今の 9,000三角形の glb をさらに Decimate で間引く。手軽だが、間引きを2回重ねると形が崩れやすく、材質の数も減らない。
- 目安に届かない種類（形が複雑なもの）は 1,500 までは許し、種類ごとの三角形の数を表に記録する。
- ファイルの大きさの見積もり: 800三角形・材質1つなら、点の数 約600〜1,200 × 32バイト（位置・向き・色）＋つなぎ方 約5KB ≒ **1ファイル 25〜45KB、14ファイルで 0.4〜0.6MB**。種類ごとに要るときだけ読むので、最初に全部は読まない。今の glb の大きさは実装の最初に測って表に足す（未計測）。
- 見た目の確認: 詳しい版と軽い版を、地図の上で見える大きさ（ズーム 17 で 150m 先くらい）で並べた画像（PNG）を作り、オーナーに見てもらう。

### 3.4 施設
- **施設に属する店は、見えている店が何軒でも（1軒でも）施設として出す**（オーナー決定）。
- 今の決まり「施設 = 輪郭 2,500m² 以上（または駅の点を含む）で、**お店が2軒以上**」の「2軒以上」は、**見えている店ではなく、読み込んだ全部の店（霧の中も含む）で数える**。数え方: 施設の輪郭（`facility.parts[0].ring`）の中にある店の点の数。輪郭の中か外かの計算だけなので軽い。施設の形を初めて計算したときに1回数えて覚える。
  - これで「霧が晴れて仲間が見えたら1軒の店が施設に変わる」「離れたら施設が1軒の店に戻る」が起きなくなる。
  - 霧の中のお店の存在が少しばれる点については「確認したいこと」に挙げる（前の段のビルでは「見えている店だけでまとめる」を採った。§3.4 は施設だけの変更）。
- 施設の店は1軒ずつの模型を描かないので、模型の数（§3.1 の 400）にも、詳しい模型の数（§3.2 の 40）にも数えない。施設は距離に関係なく全部出す（ピンは見えている店の分だけ）。
- 組の振り分けの順番: 組が1軒でも、その店に施設の情報があり、上の数え方で2軒以上なら施設の側へ回す。そのあとは並行作業の「重なる施設を1つにまとめる」処理にそのまま渡す（そこは変えない）。

### 3.5 置き方の計算を数コマに分ける
- 全部出すようにすると、初めての場所や霧が大きく晴れた直後に、数百軒の置き方の計算が一度に来る。1回で全部やると画面が止まる。
- 決めたやり方:
  - 計算待ちの店を近い順の列（キュー）に入れ、**1コマで `PLACE_BUDGET_MS` = 6ms まで**計算し、残りは次のコマへ回す（最低1軒は進める）。iPhone の速さの違いに強いよう、軒数ではなく時間で区切る。
  - 最初の1回分は今と同じく呼ばれたその場で計算する（少ない店ならすぐ出る。今のテストもそのまま通る）。
  - 地図から取り出した道路・建物（`extractFeatures` の結果）は、その列を計算し終えるまで使い回す。10m 以上動いて更新が来たら列を作り直す。
  - 計算中の見た目の更新は `LAYER_UPDATE_MS` = 250ms ごとと、列が空になったときだけ（毎コマ層を作り直すとそれ自体が重いため）。近い順なので、近くから外へ広がるように出てくる。
  - 次のコマを待つ方法（requestAnimationFrame）は ui の中に置く。テストでは手で進められるようにする。

### 3.6 ピンの数
- 増えるのはビル・施設のピンと、チェック済みの 1軒の店の ✓。
- 見積もり（前の段の実データ: 東京駅まわりの地図のお店 10,091軒のうち、2〜5軒のビルに入る店は約2,860軒＝約28%。1つのビルは平均 約2.5軒）:
  - 300軒見えているとき: ビルの店 約85軒 → **ビルのピン 約35個**。施設 2〜6個（遠くではピン1つ＋札）。
  - ズーム 17.5 以上で施設のピンが散らばると、施設1つで塊が 10〜20個 → 近くに施設が2つあれば +20〜40個。
  - ✓ の札: チェックした1軒の店の数だけ（使うほど増える。最大でも 1軒の店の数）。
  - 合計の目安: **ふだん 40〜60個、多いときで 100個前後**（今は 5〜10個）。
- 判断: 100個前後なら iPhone で大きな問題にはならない見込み。地図が動くたびの合わせ直しは「建物ごとに1回だけ測る・同じなら書かない」作りになっている。実装後に経堂・新宿で数を数え、**150個を超えるなら対策を考える**（対策は見え方が変わるので「確認したいこと」）。

### 3.7 重さの見積もり（数字）
三角形の数（お店の模型だけ。施設の立体は 1つ数千で、数個で +2〜5万）:

| 場面 | 計算 | 三角形の数 |
|---|---|---|
| 今（40軒・全部詳しい） | 40 × 9,000 | **約 36万** |
| 300軒・LOD なし | 300 × 9,000 | 約 270万（重すぎる） |
| 300軒・LOD あり | 40 × 9,000 ＋ 260 × 800 | **約 57万** |
| 上限 400・LOD あり | 40 × 9,000 ＋ 360 × 800 | 約 65万 |

描画の回数:
- 今: 出ている種類（最大14） × 模型の材質の数。材質の数は未計測（色ごとに分かれているので 1種類 十数〜数十の見込み）。実装の最初に数える。
- LOD あり: 上の「詳しい模型」の分は今と同じ（詳しい模型は最大40軒のまま）＋ 軽い模型は材質1つなので **最大 +14回**。材質を1つにしないと最大で今の約2倍になるので、§3.3 の頂点の色は必須。

iPhone での目安（この設計の上限として置く）:
- お店の模型の三角形: **合計 80万まで**（地図・霧・施設の分の余白を残す）。
- 描画の回数: お店の層で **200回まで**。
- 動き: 地図を回したり歩いたりして **30コマ/秒を下回らない**こと。
- 実機で超えたら、`LOD_NEAR_M` を縮める（例 100m）か `LOD_MAX_DETAILED` を減らす（例 30）。どちらも `config.ts` だけで変えられる。

補足: 全部の店を1つの塊として描くので、画面の外（後ろ側）の店の分も重さに入る。上の数字は「全部描く」前提で見積もっている。地域ごとに塊を分けて画面の外を飛ばす作りは、目安を超えたときの次の手として残す（今回はしない）。

### 3.8 テストの方針と実装の手順

#### domain に切り出す純粋な計算（単体テストの中心）
- `src/shops/domain/visibility.ts`
  - `visibleShops`: 上限をなくす。テスト: 500軒の晴れた店が全部・近い順で返る／今の「晴れの外」「霧の 50m」「1km」のテストはそのまま。
- `src/shops/domain/lod.ts`（新規）
  - どの店を詳しい模型にするか: 入力は「id と距離」の一覧・前回詳しかった id・`LOD_NEAR_M`・`LOD_MARGIN_M`・`LOD_MAX_DETAILED`、出力は詳しくする id の集まり。テスト: 150m 以内は詳しい／前回詳しい店は 179m でも詳しい・181m で軽い／前回軽い店は 151m で軽い／上限 40 で近い順／上限の境目で前回詳しい店が残る／空で空。
  - 模型の数の上限: 入力は「施設かどうか・距離」付きの出す物の一覧と上限、出力は残す物。テスト: 施設は数えず全部残る／施設以外は近い順に上限まで／上限ちょうど。
- `src/shops/domain/facility.ts`
  - 施設の輪郭の中にある店の数（輪郭と店の点の一覧 → 数）。テスト: 輪郭の中の2軒・外の1軒で 2／輪郭の外だけで 0。
  - 1軒しか見えていなくても施設にするかの判断（見えている数ではなく全体の数で決める）。テスト: 見えている 1軒・全体 2軒で施設／全体 1軒なら施設にしない。
  - ※ facility.ts は並行の作業者が触っている。そちらが入ってから足す。

#### infra・ui のテスト

### 3.9 config.ts に置く調整値（`src/shops/config.ts`）
| 名前 | 値（案） | 意味 |
|---|---|---|
| `MAX_SHOPS` | 削除 | 40軒の上限をやめる |
| `MAX_SHOP_MODELS` | 400 | 安全のための模型の数の上限（施設の店は数えない。ビルは1つで1） |
| `LOD_NEAR_M` | 150 | これより近い店は詳しい模型 |
| `LOD_MARGIN_M` | 30 | 切りかえの余裕。前回詳しかった店はこの分だけ遠くまで詳しいまま |
| `LOD_MAX_DETAILED` | 40 | 詳しい模型の最大の数 |
| `PLACE_BUDGET_MS` | 6 | 置き方の計算に1コマで使ってよい時間 |
| `LAYER_UPDATE_MS` | 250 | 計算中に層を作り直す間隔 |

Blender 側の値（`config.ts` ではなく台本の環境変数）: 軽い版の三角形の目安 800（上限 1,500）、外す小さい部品の大きさのしきい値。

## 4. データ・サーバー・画面の切り分け
- テーブル・RLS（データの読み書きの権限）: 変更なし。
- Edge Functions（サーバー側の処理）: 変更なし。今回の処理は全部ブラウザ側（どの店をどの模型で出すか・置き方の計算・描き方）。サーバーが要る秘密の処理は無い。
- 画面の移り変わり・状態の持ち方: 変更なし。前回詳しかった店の集まりと計算待ちの列は `attachWorld` の中に持つ（React の状態にはしない。状態管理ライブラリは入れない）。

## 5. 非機能の要件（秘密情報）
- ホットペッパーの API キーは今どおり Supabase の Secrets（`HOTPEPPER_API_KEY`）にだけ置き、Edge Function `shops-hotpepper` の中でだけ使う。ブラウザ・glb・ログ・テストのデータには出さない。この変更でキーの扱いは変わらない。
- Supabase の service_role キー（何でもできる管理用の鍵）はブラウザ側に入れない。今回の変更はブラウザ側だけなので触らない。
- 軽い模型の glb は誰でも取れる静的なファイル（`src/assets/`）になる。中身は形と色だけで、秘密は入れない。Blender の台本にもキーは書かない。
- 計測のために足すログ（三角形の数など）は、店の位置・自宅の座標・キーを出さない。調べ終えたら消す。

## 6. しないこと
- 店の中まで作り込んだ細かい模型（SPEC §9 N-27「タップしたときやすぐそばに寄ったときだけ」）。これは今回の LOD のさらに上の段で、別の段で作る。
- 施設の立体の LOD。
- 画面の外の店を描かない作り（地域ごとに塊を分ける）。目安を超えたときの次の手。
- 「重なる施設を1つにまとめる」部分の書きかえ（並行作業の担当）。
- 霧・チェックイン・ピンの見え方の変更。

## 7. 確認したいこと（オーナー）
- 施設の「お店が2軒以上」を、霧の中の店も含めた全部の店で数えてよいか（§3.4）。こうすると、霧の向こうの大きな建物に1軒しか見えていなくても施設の形で出るので、「この建物には他にも店がある」ことが少しだけ分かる。代わりの案は「2軒以上」の条件をやめ、広さ（2,500m² 以上）か駅の点だけで施設にする（1軒しか入っていない大きな建物も施設になる）。
- 詳しい模型の範囲（150m・最大40軒）と、安全の上限（400）はこの値で始めて、実機で重ければ縮めてよいか。
- 軽い模型は「遠くで見えない店の中の小物を外す」作り方でよいか（並べた画像で最終確認）。
- ピンが 150個を超える場所が出たときの対策は見え方が変わるため、その時点で相談したい（案: 遠くのビルのピンを小さい点にする／✓ を近くの店だけにする／施設のピンを散らばらせるのは近くの施設だけにする）。

- 3: 軽い模型は小物を外す作り方。並べた画像で最終確認する。
- 4: ピンが 150個を超える場所が出たら、その時に画面を見せて相談する（今は決めない）。

### 9.2 軽い模型（手順5）
作り方（`art/prototypes/blender-lod.py`。`blender-shops.py`・`blender-shop-jp.py` の中から `LOD=1` のとき読む）:
1. 元の形から作る。`LOD=1` のときは部品を作る関数（cube・cyl・sphere・lathe・tube・反った屋根）で、角の丸めを付けず、丸い形の分割を半分にする。瓦の下地は瓦の色にする（瓦を外しても色が変わらないように）。
2. **小さい部品から順に、目安（800）に収まるまで外す**。小ささは「2番目に長い辺」で比べる（細い目地・棒・瓦1枚・店の中の小物が先に外れる）。外形の箱のふちに届く部品（てっぺんの湯気・看板）と、2番目の辺が 0.2（アプリで約 1.2m）以上の部品は外さない。
3. 平らな面をまとめる（Planar）。それでも **1,500 を超えるときだけ** ふつうの間引き（Collapse）で 1,500 まで減らす。外形の箱のふちの点は動かさない。
   - 最初は §3.3 どおり「Collapse で 800 まで」を試したが、小さい箱の集まりでできた模型は壁や屋根に穴があいて崩れたため、上のやり方に変えた。
4. 材質の色を頂点の色に移し、材質を1つにする（光る窓は少し明るい色）。根元の座標は詳しい版と同じ。

### 9.4 コードでの決め方の補足（手順 2〜4・6〜8）
- 施設の「2軒以上」は、施設ごとに数えて覚え、**店の一覧（地図のお店＋ホットペッパー）が変わったときだけ数え直す**（ホットペッパーの結果があとから届いて2軒目が増える場合に施設になれるように）。
- 模型の数の上限（400）は、組（1軒の店・ビル・施設）に分けた後にかける。上限で外れた店も `shopsNear()`（近くの店の一覧）には残る。
- 詳しい・軽いは `PlacedShop.light`（true で軽い版）。顔ぶれの文字列に軽い店の id を足し、切りかえたときだけ層を作り直す。
- 置き方の計算を数コマに分ける列は `attachWorld` の中（`work`）。同じ場所（10m 未満）の更新では、取り出した道路・建物を列が終わるまで使い回す。
