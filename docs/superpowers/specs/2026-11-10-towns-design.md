# 町の機能（クリア・コンプリート・制覇率）設計メモ

日付: 2026-11-10　状態: 承認（2026-11-10 オーナー「いいよやろう」。§11 の3点も承認）　計画: docs/superpowers/plans/2026-11-10-towns.md
もとの決まり: SPEC S2（町の制覇で町全体が晴れる・半分以上）、S15（グリッド方式）、コイン 100（町の制覇）

## 1. ねらい
- お店に行くたびに「この町をどこまで食べ歩いたか」が進み、半分で町全体の霧が晴れる。区画（町）を意識して歩きたくなるようにする。
- **全国どこでも動く**（出張先でも）。**無料の枠に余裕を残す**。**チェックインや地図を重くしない**。

## 2. 決まっていること（オーナー決定）
- 町の単位: e-Stat の町丁目を、同じ市区町村の中で町名でまとめる（経堂一〜五丁目 → 経堂）。
- クリア: 町のお店の半分以上に行く → 町全体の霧が晴れる ＋ 100 コイン（1つの町で1回だけ）。
- コンプリート: 町のお店すべて（100%）。コインは無し（印だけ）。
- 判定はサーバー。記録の画面に町ごとの制覇率を出す。
- 全国で使える・無料の枠の余裕の中・動作を重くしない（2026-11-10）。

## 3. 方式の比較と、選んだ案

| | A. 全国を先に全部取り込む | B. 境目も数も都度取る | **C. 境目だけ先に全国分をファイルで置き、数は初めての町だけ数えて覚える（採用）** |
|---|---|---|---|
| 全国で動く | ○ | ×（地図のデータに町の形が無い） | ○ |
| データベース（無料 500MB） | 100〜200MB を先に使う | 小 | 行った町だけ（1町 数KB） |
| 最初の準備 | お店数えに数時間 | なし | 境目のファイル作りだけ（30分〜1時間） |
| チェックインの速さ | 変わらない | 毎回重い | 変わらない（町の計算は後ろで別に動く） |
| 町の決まりを変えたとき | 全国やり直し | — | ファイルを作り直すだけ |

C を選ぶ。全国で動き、データベースをほぼ使わず、重い処理は「その町に初めて誰かが行ったとき」の1回だけになる。

|---|---|---|---|---|
| 東京都 | 5.7MB | 1,858 | 2.3MB | 0.45MB |
| 北海道 | 16.1MB | 8,106 | 13.3MB | 2.9MB |
| 長野県 | 7.4MB | 2,803 | 4.9MB | 1.0MB |

- 全国の実測（2026-11-10 夜、`scripts/towns/build.ts` で47都道府県を作った）: 町 **141,920**、ファイル **1,025**（格子 1,024＋一覧）、圧縮後の合計 **58.9MB**（Supabase のファイル置き場は無料で 1GB。6% ほど）。いちばん大きい格子は `543_139`（大阪のあたり）で、元 1.97MB・圧縮後 0.37MB。
- 町の広さ: 東京は半分が 0.6km² 以下・9割が 2km² 以下。北海道は 20km² を超える町が 981、最大 804km²。→ 広い町の扱いが要る（§6・§7）。

## 4. 全体の流れ
```
[1回だけ] e-Stat の境目 → まとめる・ならす → 0.25度の格子ごとのファイル → Supabase のファイル置き場（非公開）

チェックイン（今までどおり・速さは変えない）
   └→ アプリが後ろで関数 towns を呼ぶ
        1. 行ったお店がどの町か（まだ分かっていない店だけ。格子のファイルを1つ読んで形の中か調べる）
        2. その町のお店の一覧が無い・30日より古い → 地図タイルから数えて覚える
        3. 行った数／全部の数 → 半分以上でクリア（+100）、全部でコンプリート
        4. 町ごとの進み具合と、今回新しく取れたものを返す
アプリ: クリアした町の形を読み、その形の中の霧を晴らす。記録に制覇率を出す。
```

## 5. データ

### 5.1 境目のファイル（先に作る）
- もと: e-Stat「国勢調査 2020年 小地域（町丁・字等）境界データ」世界測地系・緯度経度・Shapefile、都道府県ごと。
- 作り方（`scripts/towns/` の台本、mapshaper を使う）:
  - 水面（HCODE 8154）は除く。
  - 町名 = `S_NAME` の末尾の「◯丁目」（漢数字・数字）を取ったもの。空なら市区町村名。
  - 同じ市区町村（PREF＋CITY）で同じ町名のものを1つの形にまとめる。
  - 10m でならす。座標は小数5桁。
  - `town_id` = `<PREF><CITY>-<町名>`（例 `13112-経堂`）。名前は「経堂」、市区名「世田谷区」も持つ。
- 置き方: 緯度・経度を 0.25度で区切った格子ごとに1ファイル（gzip した JSON、`g/<格子>.json.gz`）。町は、形の部品（飛び地・島）ごとの外側の四角が触れる格子すべてに入れる（町全体の四角だと、離れた島のある町が間の格子にも入ってしまうため）。あわせて、ファイルのある格子の一覧 `g/index.json` を置く（実装で足した。下の「実装で決めたこと」）。Supabase のファイル置き場の非公開バケット `towns`。読むのは関数だけ。
- 開発用と本番用の Supabase の両方に置く（まず開発用）。置く作業はオーナーに1回お願いする（手順書を書く）。

### 5.2 データベース（migration 0005）
- `towns`（今ある表）に足す: `city_name text`、`area_m2`、`shops jsonb`（その町の地図のお店 `[{id:'osm:…', name, lat, lng}]`）、`counted_at`、`count_state jsonb`（数えている途中の続き。終われば null）。**行は、誰かが行った町だけ**（関数が初めてのときに入れる）。
- `shops.town_id`（今ある列）に、その店の町を入れる。
- `town_conquests`（今ある表）に `completed_at timestamptz null` を足す。`conquered_at` がクリアの時刻。
- SQL 関数 `grant_town(p_user, p_town, p_clear, p_complete)`: クリアの行とコイン 100（`coin_ledger` の `town_conquest`）を1つのトランザクションで。二重には付かない（今ある一意の決まり）。service_role だけが呼べる。
- **`fog_cells` に町のセルは入れない**（SPEC からの変更。§7）。

## 6. サーバーの関数 `towns`（`supabase/functions/towns/`）
- 入力なし（ログインしている人の分を計算）。出力: `{ towns: [{ id, name, city, visited, total, clearedAt, completedAt, counting }], newly: [{ id, name, kind: 'clear'|'complete', coins }], more }`。
- **町を決める**: その人のチェックインした店のうち `town_id` が空のもの（1回に最大 20 軒）。店の位置の格子のファイルを読み、形の中にある町を探す。見つからなければ（海の上・データの外）そのまま空で、次からは調べない印を付ける。
- **お店を数える**: z14 の地図タイル（アプリと同じ OpenFreeMap、同じ `FOOD` の種類、名前つき）から、町の形の中にある点を集める。形に触れるタイルだけ読む。
  - 1回の呼び出しで読むタイルは **最大 40 枚**（関数の CPU は1回 2秒まで）。残りは `count_state` に覚えて、次の呼び出しで続きから。その間は `counting: true`、判定はしない。
  - 30日より古い一覧は、その町で次に誰かがチェックインしたときに数え直す（閉店・開店を追う）。
- **数え方**:
  - 分母 = 町の一覧の数 ＋ その人が行った「一覧に無い店」（ホットペッパーだけの店など）の数。
  - 分子 = 行った店の数。一覧の店と行った店は、`osm:` の番号が同じ、または 40m 以内で名前が互いを含む（今の合体と同じ決まり）なら同じ店。
  - クリア: 分子 ≥ 分母 ÷ 2 の切り上げ。コンプリート: 分子 = 分母（分母 1 以上）。
  - 一度取ったクリア・コンプリートは、あとで分母が増えても消さない。
- チェックインの関数は変えない。町の計算が失敗しても、チェックインは成功のまま。次に記録を開いたとき・次のチェックインでやり直す。
- 置き方の制約: ダッシュボードのエディターは同じフォルダのファイルだけなので、`core.ts`（純粋・vitest で試す）、`index.ts`、タイルを読むファイルを `towns/` に置く。

## 7. アプリ側
- 新しいフォルダ `src/towns/`（`domain/` 形の中か・形をセルに直す・進み具合の型、`infra/` 関数の呼び出しとクリアした町の形の読み込み、`ui/` 記録の町の一覧とクリアの帯）。
- **霧**: クリアした町の形を持ち、**雲を置く範囲の中だけ**セルに直して「晴れた場所」に足す（地図は現在地から 1.2km、記録は 3km）。町が 800km² あっても、計算するのは見えている範囲だけ。
  - サーバーに町のセルを保存しない理由: 1.5km² の町で 2,400 行、広い町は 100万行を超え、無料の 500MB をすぐ使い切るため。
- **チェックインのあと**: 後ろで `towns` を呼ぶ。`more` や `counting` の間は数秒おきに呼び直す（最大 15 回）。`newly` にクリアがあれば「◯◯ クリア！ +100」の帯を出し、町の霧を晴らす。コンプリートは「◯◯ コンプリート！」。
- **記録**: 今ある「町のクリア・コンプリート（準備中）」の枠を、町の一覧にする。1行 = 町名（市区名）・行った数／全部・棒・クリア／コンプリートの印。並びは最近行った町から。数えている途中は「数えています…」。見た目は実装のときに画像でオーナーに確認する。
- **晴れた広さ**（記録・マイページ・実績の広さ）: セルの数 ＋ クリアした町の面積（町の中にあるセルは二重に数えない）。日付スライダーでは、クリアした日から町が晴れる。
- **出典**: スプラッシュと設定に「出典: 政府統計の総合窓口（e-Stat）」「『国勢調査 町丁・字等別境界データ』（総務省統計局）を加工して作成」。

## 8. 重さと無料の枠の見積もり
| | 使う量 | 枠 |
|---|---|---|
| ファイル置き場 | 58.9MB（実測） | 1GB |
| データベース | 行った町 1つ 数KB〜数十KB（1,000 町で 5〜20MB） | 500MB |
| 関数の呼び出し | チェックイン1回につき 1〜2回 | 月 50万回 |
| 関数の CPU | 格子のファイル1つ（最大 元 1.97MB・圧縮後 0.37MB）＋タイル最大 40 枚 | 1回 2秒 |
| Vercel | 増えない | — |
- チェックイン: 変わらない。初めての町のときだけ、後ろの計算に 1〜3秒（画面は止まらない）。
- 起動: クリアした町の形を読む1回が増える（1町 1〜4KB）。

## 9. やらないこと（今回）
- 今いる町の名前や進み具合を地図の上に常に出すこと（行ったことの無い町は数が分からないため。次の候補）。
- 町の境目の線を地図に描くこと。
- 町を使う週ミッション・実績（週ミッションの段で）。
- ほかの人との比べ合い。

## 10. 作る人に任せること
- 格子のファイルの中の JSON の細かい形、gzip の読み方。
- 形をセルに直す計算の書き方（走査線など）。
- 記録の町の一覧の細かい見た目（画像で確認してから）。
- 置く作業の手順書の書き方。

## 11. オーナーに確かめた点（3つとも承認 2026-11-10）
1. **広い町も、半分行けば町全体が晴れる**（SPEC どおり・上限なし）。山あいでは1軒で数十〜数百km² が晴れることがある。重さは問題ない（見えている範囲だけ計算）。
2. 行った店が地図の一覧に無いとき（ホットペッパーだけの店）は、その人の分母と分子の両方に足す。→ どの店に行っても必ず進む。
3. 町のセルをサーバーに保存しない（SPEC S15・「サーバーには店周りと町制覇のセル」からの変更）。SPEC も合わせて直す。

## 12. 実装で決めたこと（2026-11-10 夜。作る人に任された範囲と、足したもの）
- **格子の一覧 `g/index.json`**（`{ v: 1, keys: [...] }`）を置く。「この場所に町が無い（海など）」と決めるのは、一覧が読めて、その格子が一覧に無いときだけ。一覧やファイルが読めないときは「町なし」と決めず、次の回にやり直す（読めなかっただけで町なしと覚えてしまうのを防ぐ）。
- 格子のファイルの形は `{ v: 1, towns: [{ id, name, city, area, bbox, geom }] }`。関数は gzip かどうかを先頭の2バイトで見分ける。
- 町の形が無い・市区町村の番号が無いものは作るときに外し、都道府県ごとに外した数を出す（東京は 1）。
- お店を数える所: タイルを読む前に「名前のある飲食店」だけにふるう。1回に読むタイルは最大 40 枚、続きは `towns.count_state` に覚えて次の回に続ける。
- クリアのコインは `core.ts` の `TOWN_COINS = 100`、書くのは SQL の `grant_town` だけ（service_role だけが呼べる。町1つにつき1回）。
- アプリ側: 町の形をセルに直すのは走査線（`src/towns/domain/shape.ts` の `cellsInTown`）。同じお知らせ（町＋種類）は1回だけ出す。クリアした町の読み込みに失敗したら、空ではなく失敗として扱う。
- 見た目: 記録の一覧は、旗（クリア）・かんむり（コンプリート）の印、半分の所に線のある細いゲージ、右に「行った数 / 全部」と％。色は記録・お店のシートと同じ（クリーム・茶・オレンジ）。顔つきの絵や紙ふぶきは使わない（オーナー: 「幼稚向けにしなくていい、クオリティだけあげて」）。
- 作る台本は格子ごとの ndjson に書き足してから固める（全国でもメモリを食わない）。全国で 20分ほど、e-Stat へは1秒おきに47回。
